# チョイアプリ・フィードバック 2026-09 — シェル/設定 UI の改善記録

作成日: 2026-09-01。トラックA（保守者向け）。

「チョイアプリ」= このテンプレートをコピーして作る、担当者数人・単機能の
小さな業務アプリ（オーナーの呼称。テンプレート利用の最頻ユースケース）。
そのフィードバック 4 件と、それぞれの判断・実装を記録する。コードコメントの
`choiapp-feedback-2026-09 §N` はこの文書の節を指す（conventions §12 の参照文法）。

## 1. 受け取ったフィードバック

1. チョイアプリ作成時はデフォルトでログイン機能無しが便利。アプリが育った後に
   ログイン機能を追加する経路がほしい。
2. 設定が一つにまとまっているより、分類分けされている方がよい。
3. ヘッダと左ペインがメインと連動してスクロールするのは使いにくい。
4. ヘッダや左ペインに通知バッジやステータス表示が標準でほしい。

2〜4 は本フィードバック対応の PR で実装済み（§2〜§4）。1 は既存経路の案内 +
デフォルト化の提案として記録し、オーナー判断待ち（§5）。

## 2. シェルの固定スクロール（フィードバック 3）

`Header.svelte` / `Sidebar.svelte` を `position: sticky` にし、本文スクロール
中もヘッダと左ペインを画面に固定した。

- **inner scroll ではなく sticky を選んだ理由**: ドキュメント自体を唯一の
  スクロールコンテナに保つため。`main` を `overflow-y: auto` の内側スクロールに
  する案は、SvelteKit のスクロール復元・アンカーリンク・Playwright の
  `fullPage` スクリーンショット（visual スイートの土台）をすべて壊すか特別
  対応が必要になる。sticky はどれも素通しで動く。
- サイドバーは `height: 100vh`（`100dvh` フォールバック付き）+
  `overflow-y: auto` で、ナビが縦に溢れる派生アプリでも自前スクロールする。
- z-index の階層は Header.svelte のコメントが一次情報（ページ内フロート
  ≦30 < ヘッダ 100 < モバイルドロワー 850/900 < パレット/トースト 1000）。
- 設定ページのカテゴリアンカー（§3）は sticky ヘッダの分だけ
  `scroll-margin-top` で着地位置を下げる。

## 3. 設定ページのカテゴリ分け（フィードバック 2）

`settings/+page.svelte` のカードを 5 カテゴリの節（`<section>` + 見出し +
カテゴリ内グリッド）に再編し、ページ先頭にアンカージャンプのカテゴリナビを
置いた。

| カテゴリ | id | カード | 表示条件 |
| --- | --- | --- | --- |
| 外観・言語 | `appearance` | テーマ / 言語 / ウィンドウ効果 | 常時（効果は Tauri+admin+対応時） |
| アカウント | `account` | パスワード変更 / 自動ログイン | 常時（自動ログインは Tauri+admin） |
| サーバ・接続 | `connectivity` | LANアクセス / システム情報 | admin |
| データ管理 | `data` | 監査ログ保持 / バックアップ・リストア | admin かつ実バックエンド |
| セキュリティ | `security` | 認証を無効化 | Tauri かつ管理可（M11 の escape hatch 含む） |

- **タブではなくアンカーにした理由**: 全カードが 1 ページに残るので、e2e
  スモーク/visual/axe の各スイートが「開いたら全部見える」前提のまま通り、
  スクロールしないほど設定が少ない派生アプリではナビが単に無害になる。
  カテゴリナビは表示中の節だけを載せる（capability-hide、spec §11.3 と同じ
  流儀で、権限外の項目をグレーアウトで見せない）。
- 旧「Danger zone」カード（visual-refresh plan Phase 5）は解体し、認証無効化
  → セキュリティ、バックアップ/リストア → データ管理へ移した。危険系カードは
  `.danger-card`（枠色 `--banto-danger`）で従来の警告色を維持し、確認
  ダイアログ・文言・ハンドラは一切変えていない。
- 見出し階層は h1（ページ）> h2（カテゴリ）> h3（カード）> h4（カード内小見出し）。

## 4. ナビバッジとヘッダステータス（フィードバック 4）

### 4.1 サイドバーの未確認更新バッジ

- 機構: `$lib/navBadges.svelte.ts`（カウント保持）+
  `routes/(app)/+layout.svelte`（配線）+ `Sidebar.svelte`（描画）。
  `NavItem.badgeResource`（`$lib/navigation.ts`）を宣言したエントリだけが対象。
- 供給源は admin-core の `invalidate()` バス（spec §3.4）。**自クライアントの
  ミューテーションも `resource_changed` サーバイベント（spec §3.5、SSE/Tauri
  両輸送）も同じバスに合流する**ため、輸送別の配線が要らず、デモモードでも
  そのまま動く。「そのリソースのページを開いている間のイベント」は未確認では
  ない（ページ側のリストが即時再取得する）のでカウントしない。ページに着地
  したらクリア。永続化しない（セッション内の「前に見てから変わった」ヒント）。
- テンプレート同梱の宣言は `items` のみ（デモ）。派生アプリは自リソースに
  `badgeResource` を足すだけでよい。invalidate バス外の供給源は
  `navBadges.increment(path)` を直接呼ぶ。
- e2e: smoke シナリオ 13 が REST+SSE 実経路で「別クライアントの変更 →
  バッジ表示 → 再変更で加算 → ページ訪問でクリア」を検証。

### 4.2 ヘッダのステータス表示

ヘッダ中央（スペーサ右）に `StatusBadge` のチップ列を追加。表示は
「該当する状態のときだけ」:

- デモモード（`getBantoMode() === 'demo'`）: info チップ。従来はデモで動いて
  いることを示す表示が皆無だった。
- ログイン不要モード（M11、`sessionStore.authDisabled`）: warning チップ。
  従来はユーザーメニューが消えるだけで、モードが「見えない」状態だった。
- 通常ログイン時: 現在ロール（管理者/編集者/閲覧者）の neutral チップ。

付随修正: info バッジをヘッダ経由で全ページに出したことで、`StatusBadge`
info 変種の文字色コントラスト不足（4.1:1 < 4.5:1）が axe スイートに検出され、
`--banto-primary-hover` 化で修正（Sidebar `.nav-item.active` と同じ既知
パターン。users ページのロールバッジにも遡って効く）。

## 5. ログイン無しデフォルト（フィードバック 1）— 現状の経路と提案

**現状でも「ログイン無しのチョイアプリ」への経路と、育ってからログインを
足す経路は両方ある**（M11 ログイン不要モード。トラックB の手順は
[docs/recipes/no-login-app.md](recipes/no-login-app.md)）:

1. 初回セットアップで管理者アカウントを 1 つ作る（現状スキップ不可）。
2. 設定 → セキュリティ →「認証を無効化」を ON（Tauri のみ、LAN アクセスと
   排他）。以後ログイン画面なしで起動する。
3. 育ったら同じトグルを OFF に戻すだけでログイン運用に移行できる
   （どのロールの synthetic session からでも戻せる escape hatch は
   `auth_config_apply` の Rust doc コメント参照）。

**未実装 = 「デフォルトで無し」**。初回セットアップ画面に「ログインなしで
使い始める」を置く（= ユーザー 0 人のときに限り `auth_config_apply` を許す
ブートストラップ窓を開ける）のが素直な実装だが、

- 認可ゲートの変更（ユーザー 0 人判定）はセキュリティ不変条件側の設計判断で、
  REST 側セットアップ（`banto-serve` 経由の初回画面は LAN 文脈）と挙動を
  どう非対称にするかの整理が要る（M11 は v1 で Tauri 窓限定）。
- src-tauri はサンドボックスでコンパイル検証できない（AGENTS.md）。

ため、この PR では実装せず提案として残す。採否はオーナー判断
（採用時は roadmap にマイルストーンを切り、ADR で代替案比較を残すこと）。
