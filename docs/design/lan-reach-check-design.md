## 1. 目的 — 「ルールがある」と「届く」を分ける

Issue #219 は、設定 > サーバ・接続で次の 4 つを**別々に**出すことを求めている。

1. サーバーの待受状態と接続範囲（#462 の `live`。済み）
2. Windows ファイアウォールの許可ルールの状態（PR-B。済み）
3. ベンダー製品側の許可状態（判定できないので「未確認」。PR-A の一般の案内）
4. **別の端末からの接続確認の結果**（本書）

1〜3 は「通るはずの条件」で、4 だけが「実際に通った事実」になる。ルールがあっても、ベンダー製品・集中管理・
明示的な遮断・ルーター・Wi-Fi の端末間の分離（AP アイソレーション）・別のサブネットで届かないことがあるし、
ルールが見えなくても届くことがある（PR-B の「確認できない」、ほかの許可ルール）。だから 4 は 1〜3 から推測せず、
**実際に別の端末からサーバーへ届いた要求**だけを根拠にする。

### 1.1 保証すること

- **その時刻に、その接続元 IP の端末から、その待受（generation・ポート）へ、TCP の要求が届いて応答できた**こと。
- 根拠はサーバー側で観測した値だけ: サーバーの時計、ソケットの接続元（`ConnectInfo<SocketAddr>`）、
  その要求を受けた待受の `generation` とポート。クライアントの自己申告（本文の値・`X-Forwarded-For` 等）は使わない
  （監査の優先 4）。

### 1.2 保証しないこと（画面にも書く）

- **ほかの端末**から届くこと（同じ Wi-Fi でも、別のサブネット・VLAN・VPN の端末は別）。
- **いまも**届くこと（確認の後にルール・ベンダー製品・ネットワークが変われば届かなくなる）。
- 経路の途中の機器（ルーター・スイッチ・AP）の設定がすべて正しいこと。確かめたのは「この 1 本の経路」だけ。
- 待受の**どの NIC の IP** へ届いたか（`0.0.0.0` で待ち受けるとき。§3.6、D7）。記録するのは端末が宛先として
  使ったホスト（`Host`）とポートで、ポートはサーバー側の値、ホストは発行した URL と一致したものだけを受け付ける。
- **このPC自身**からのアクセスは、別の端末の確認として数えない（Issue 本文「自身へのローカルアクセスだけでは
  別端末からの到達性を保証しない」）。自分自身への接続はファイアウォールの受信の規則を通らないことがある。
- 期限内に記録が無かったことは、**届かないことの証明ではない**（読み取らなかっただけかもしれない）。

## 2. 仕組みの案と比較

### 2.1 (A) 使い捨ての確認トークンを QR / URL で渡す（推奨）

1. 管理者の画面（Tauri、admin）が「別の端末から確認」を押すと、Tauri コマンドが**推測できない使い捨てトークン**を
   発行する。トークンは、発行した時点の `generation`・待受のポート・端末に開かせるホスト（`live` の URL のうち
   管理者が選んだ 1 つ）に結び付く。短い有効期限（D4、推奨 5 分）・1 回限り。
2. 画面に、その URL を QR と文字で出す: `http://<host>:<port>/reach#t=<token>`。
   トークンは**フラグメント（`#` の後ろ）**に入れる（§3.2）。
3. 別の端末がその URL を開くと、LAN のサーバーが SPA を返し、SPA の `/reach` ページがフラグメントからトークンを
   読んで `POST /api/reach-check`（本文 `{ "token": "…" }`、`X-Banto-Client` ヘッダー付き）を送る。
4. サーバーは**トークンを照合**し、通れば到達を記録する（記録: サーバーの時刻・ソケットの接続元 IP・`Host` の
   ホストとポート・その待受の `generation`・トークンの通し番号）。トークンは使用済みにする。
5. 管理者の画面は、Tauri コマンドで結果を読む（トークンが有効な間だけ数秒おきに読み直す。D9）。

### 2.2 (B) トークン無し（誰でも叩ける記録の口）— 却下

`POST /api/reach-check` を無条件に受け付け、最後に届いた接続元を記録する案。

- **偽装・汚染**: LAN の誰でも（管理者が確認していない時間にも）「確認済み」を作れる。スクリプトで叩き続ければ、
  管理者が確認したい端末の記録を押し流せる。
- **どの確認の結果か分からない**: 管理者が「いま QR を開いた端末」と、前から置かれている壁のモニターの再読み込みや
  ポートスキャナーの要求を区別できない。
- **古い結果の引き継ぎ**: 発行の単位が無いので、待受の変更（generation）や時刻との結び付けが曖昧になる。
- 記録の量を抑えるにはレート制限に頼るしかなく、上限まで汚された状態が「確認済み」に見える。

監査の優先 4「古い結果を引き継がない」「対象 URL/bind/port/起動世代へ結び付け」を満たせないので採らない。

### 2.3 (C) 管理者の PC 自身から LAN の IP へ接続して確かめる — 却下

Tauri 側から `http://<自分の LAN の IP>:<port>/` へ接続して成功を見る案。端末が要らず手軽だが、

- 宛先が自分自身の IP の接続は、OS の中で折り返され、**受信のファイアウォールの規則を通らない**ことがある。
  ルールが無くても成功し得るので、何も保証しない。
- Issue 本文の要件「自身へのローカルアクセスだけでは別端末からの到達性を保証しない」に正面から反する。
- ルーター・AP・ベンダー製品の LAN 側の制御も一切通らない。

「サーバーが動いている」ことの確認は既に `live` で分かるので、この案を足しても新しい情報は無い。採らない。

### 2.4 推奨

**(A) を採る。** 実装の細部の選択（トークンの置き場所、ページの作り方、記録の範囲）は §3 と D1〜D10。

## 3. 安全面（推奨案 (A)）

### 3.1 認証していない LAN の端末に許すのは 1 つの口だけ

- 増える未認証の口は **`POST /api/reach-check` の 1 つだけ**。静的な SPA（`/reach` を含む）は今も未認証で配っている
  （ログイン画面と同じ）ので、配るものは増えない。
- この口は**セッションを発行しない**。応答にトークンやベアラーを含めず、成功しても `/api/*` の他のルートは
  401 のまま。`AuthState`・grant・`require_auth` には触らない（grant の「昇格経路を作らない」を、そもそも
  identity を持たないことで満たす）。
- 閲覧公開（#189）・ログイン不要モードの設定とは**独立**に動く（オフでも動く。オンでも挙動は同じ）。
  トークンを持たない要求は、閲覧公開がオンでも記録しない。
- `X-Banto-Client` の CSRF ヘッダーは他の `/api/*` と同じく必須（`api_router` の層の内側に置く）。
- security headers は最外層の `with_security_headers` がそのまま掛かる（conventions §6）。CSP は変えない
  （`/reach` のページの `fetch` は `connect-src 'self'` で足りる）。

### 3.2 トークンの渡し方 — フラグメントと POST

- トークンは URL の**フラグメント**に入れる。フラグメントは HTTP の要求に乗らないので、サーバー・プロキシの
  アクセスログ、`Referer`、要求行に残らない。`/reach` ページは読んだ直後に `history.replaceState` で
  フラグメントを消す（端末の履歴に残さない）。
- 記録は **GET ではなく JavaScript からの POST** でだけ行う。チャットアプリのリンクのプレビュー・プリフェッチ・
  ブラウザの先読みが、人が開く前にトークンを消費してしまうのを防ぐ（それらは SPA の JavaScript を実行して
  POST しない）。`X-Banto-Client` ヘッダーを付けられるのも JavaScript の `fetch` だけ。
- 対案（GET `/reach?t=…` にサーバーがその場で HTML を返す）は D2 で比べる。

### 3.3 トークンの強度・期限・回数・数

- **強度**: セッションのトークンと同じく `uuid` の v4（OS の乱数、122 ビット）。依存は増えない（conventions §3。
  `uuid` は既に `banto-server` の依存）。D3 で 2 つ連結（244 ビット）にするかを決める。
- **期限**: 発行から 5 分（D4）。期限はサーバーの単調な時計（`Instant`）で判定する。
- **1 回限り**: 照合に通ったら使用済みにする。使用済み・期限切れ・別の世代のトークンはすべて同じ失敗の応答
  （`unusable`）にして、どれに当たったかを外に教えない。
- **同時に有効な数**: 1 つ（D5）。新しく発行すると前のトークンは失効する（画面に出す QR は 1 つなので）。
  発行は admin の Tauri コマンドだけなので、上限は発行の暴走ではなく「どの QR が生きているか」を明確にするため。
- **このPC自身からの要求は消費しない**（§3.6）。管理者が自分の画面で URL を開いてしまっても、そのまま
  スマートフォンで読み取り直せる。

### 3.4 照合は定数時間

- 有効なトークンは高々 D5 の数（推奨 1）なので、`HashMap` で引かず、**有効なトークンを全部なめて**バイト列を
  定数時間で比べる（長さが違えば即座に偽でよい — 長さは公開情報。比較は自前の 10 行ほどの XOR の畳み込み。
  `subtle` 等の依存は足さない）。
- 期限・世代・使用済みの判定は、比較で一致したものに対してだけ行う（一致しない要求で分岐の時間差を作らない）。

### 3.5 待受の世代に結び付ける（`server_apply` で無効になる）

- トークンは発行時の `generation` を持つ。発行は Tauri 側で `state.server` のロックを取って `generation`・`live` を
  読んだうえで行う（PR-B の `firewall_rule_status` と同じ読み方）。待受が無い・loopback のみ・IPv6 のときは
  発行しない（PR-A の「出さない条件」と同じ判定。コード `notListening` / `loopbackOnly` / `unsupportedBind`）。
- `server_apply` が `generation` を進めるとき（同じロックの中）に、トークンの保管所の世代も進め、**発行済みの
  トークンと、記録済みの結果を両方とも捨てる**（古い結果を引き継がない。監査の優先 4）。grant の
  `GrantGeneration` と同じく、「世代を読んでから発行」と「世代を進めて失効」が同じロックで直列化され、
  止まっていた発行が失効の後に紛れ込まない。
- 待受ごとのルーターは、自分の `generation` とポートを持つ（`start_embedded_server` で組み立てるときに渡す）。
  照合は「トークンの世代 = その要求を受けたルーターの世代 = 保管所の今の世代」のときだけ通す。止めている途中の
  古い待受に届いた要求は記録しない。
- 記録するポートは**その要求を受けた待受のポート**（サーバー側の値）。`Host` のポートが違えば通さない。

### 3.6 接続元とこのPC自身の判定

- 接続元は `ConnectInfo<SocketAddr>`（`MaybePeerAddr`）だけを使う。無ければ拒否する（fail closed。grant の
  `require_loopback_peer` と同じ扱い）。`X-Forwarded-For` 等は読まない。IPv4 射影の IPv6
  （`::ffff:a.b.c.d`）は IPv4 に直して扱う（`server.rs` の正規化と同じ）。
- 次のどれかなら**このPC自身**として扱い、到達の記録にしない（トークンも消費しない）。結果には「このPC自身からの
  アクセスがあった」ことだけを残し、画面で「別の端末の確認にはなりません」と出す。
  - 接続元が loopback（`127.0.0.0/8`、`::1`）。
  - 接続元が**このPCのインターフェースのアドレス**のどれか（`if-addrs` で列挙。`lan_urls_for_bind` と同じ依存。
    要求ごとに列挙するのは重いので、発行時に列挙して保管所に持ち、照合時は比べるだけにする。発行と照合の間に
    アドレスが変わる隙は D4 の期限の内側に限られる）。
- 同じホストのリバースプロキシの後ろでは接続元がすべてプロキシ（loopback）になり、この判定で全部が
  「このPC自身」になる。Tauri の組み込みサーバーはプロキシを前提にしないので、これは文書（レシピ）で注意する
  だけにする（ADR-0017 §6 と同じ扱い）。

### 3.7 宛先ホスト（`Host`）の扱い

- 発行時に、管理者が選んだ URL のホスト（`live` の `urls` のうち loopback 以外の 1 つ）を保管所に持つ。
- `Host` ヘッダーのホストとポートがそれと一致しないときは通さない（`unusable` ではなく `hostMismatch`。照合は
  トークンが一致した後に行い、トークンは
  消費しない）。`Host` は相手が決められる値なので、これは「別の URL へ貼り替えて使われた」ことを弾くための検査で、
  届いた NIC の証明にはならない（§1.2）。記録する「使った URL」は、一致を確かめた発行時のホストとサーバー側の
  ポートで組み立てる（受け取った文字列そのものは画面に出さない）。

### 3.8 記録の量とレート制限

- 記録はメモリだけに持ち、永続化しない（アプリの再起動・待受の変更で消える）。保管所が持つのは「今の世代の
  有効なトークン（D5）」「到達の記録（最新の数件。推奨 8 件で古い順に捨てる）」「このPC自身からのアクセスの
  有無（真偽と最後の時刻だけ）」だけ。
- 未認証の口なので、失敗した照合（`unusable` / `hostMismatch`）に**接続元 IP ごとの回数制限**を掛ける
  （推奨: 1 分に 10 回で 1 分止める。超えたら照合もせずに 429）。数える IP の表は上限付き（推奨 256、古いものから
  捨てる）。照合自体は軽い（argon2 のような重い検証は無い）ので、目的は CPU ではなく、総当たりの試行回数と
  メモリを抑えること。122 ビットの総当たりは制限が無くても現実的でないので、制限は多層防御（D6）。
- 成功した照合は回数に数えない（1 回限りなので繰り返せない）。

### 3.9 ログと監査

- **トークンそのものは、どこにも残さない**（監査の `detail`・`eprintln!`・応答・記録のどれにも。conventions §6
  「監査 detail に秘密を入れない」）。記録と画面で識別に使うのは、発行ごとの通し番号（秘密ではない）。
- 推奨は**監査しない**（D8）:
  - 発行は永続する状態を変えない（メモリの使い捨ての値）。grant の発行を監査しないのと同じ扱い。
  - 到達の記録は資格情報なしで叩ける口なので、監査に書くと増幅の経路になる（conventions §1 の Issue #278 の
    規約「資格情報なしで叩ける認証系は監査を増幅させない」）。
  - 発行の結果は管理者の画面に出るので、操作の記録の目的は画面で足りる。
- 失敗した照合は記録もログもしない（回数制限の数だけを持つ）。

### 3.10 応答の中身と文言

- REST の応答は**コードと値だけ**（conventions §13: Rust に文言を持たない）。既存の `ErrorBody` には
  文言を運ぶ `Other { message }` / `BadRequest { message }` しか合う種類が無い（ログインの 429 は日本語の
  `message` を返している）ので、この口は専用の小さな形 `{ "result": "<コード>" }` で返す:
  - 成功: `200 { "result": "recorded" }`
  - このPC自身: `200 { "result": "selfAccess" }`
  - 使えないトークン: `404 { "result": "unusable" }`（使用済み・期限切れ・別の世代・形が不正を区別しない）
  - ホストの不一致: `409 { "result": "hostMismatch" }`
  - 回数制限: `429 { "result": "rateLimited" }`＋`Retry-After`
  - 接続元が分からない: `403 { "result": "unusable" }`（fail closed。端末から見れば使えない URL と同じ）
  - CSRF ヘッダーが無い・本文が JSON でない: 既存の層の応答のまま（403 / 400）
- 応答に、サーバー側の情報（PC の名前・他の IP・ポートの一覧・接続元 IP）は入れない。端末側に出すのは
  「記録しました」「使えない URL です（期限切れ・使用済み・待受が変わった）」「このPC自身からのアクセスでした」
  「しばらく待ってから」だけ。
- 文言は `/reach` ページ（Svelte）の Paraglide のキー（en / ja）に置く。サーバーが HTML を組み立てないので、
  §13 と §7（`{@html}`）の規約に新しい例外を作らない。

## 4. 表示

### 4.1 管理者の画面（設定 > サーバ・接続）

PR-A の「許可に必要な情報」・PR-B の「ルールの状態」とは**別の欄**（`LanReachCheckPanel`）にし、
ファイアウォールの状態から結果を推測しない・結果からファイアウォールの状態を推測しない。欄を出す条件は PR-A と
同じ（Tauri・稼働中・loopback 以外・IPv4）。Windows 以外でも出す（到達の確認は OS に依らない。PR-A の欄は
Windows のファイアウォールのものなので Windows 限定だった）。

| 状態 | 出すもの |
| --- | --- |
| 未確認 | 「別の端末からの接続はまだ確認していません」＋「別の端末から確認」ボタン（URL の選択） |
| 確認待ち | QR と URL（コピー可）、残り時間、「別の端末で読み取ってください。このPCで開いても確認になりません」 |
| 確認済み | 「別の端末から到達を確認しました」＋時刻（絶対時刻と「n 分前」）・接続元 IP・使った URL（`http://<host>:<port>`）。注記「この時点に、この端末から届いたことの確認です。ほかの端末や、いまも届くことは保証しません」 |
| 確認済み（古い） | D10 の時間を過ぎたら、同じ内容を弱い表示にして「時間が経っています。必要ならもう一度確認してください」 |
| このPC自身 | 「このPC自身からのアクセスがありました。別の端末の確認にはなりません」（確認待ちは続く） |
| 期限切れ | 「期限内に別の端末からのアクセスはありませんでした」＋案内（同じネットワークか、上の許可の情報・ルールの状態、ベンダー製品、AP の端末間の分離）。**届かないとは断定しない** |
| 読めない | IPC の失敗・応答の形が違う → 「状態を読めませんでした」。「未確認」にしない（PR-B の「読取失敗≠ルールなし」と同じ） |

- 待受が変わったら（`generation` の変化）、結果は捨てて「未確認」に戻す。古い待受での結果を「以前の結果」として
  残すこともしない（監査の優先 4）。
- 時刻はサーバーの記録した時刻（UNIX ミリ秒）を画面のロケールで出す。サーバーと画面は同じ PC なので時計の
  ずれは無い。
- 確認済みの記録が複数ある（別の端末で続けて確認した）ときは、新しい順に最大数件（§3.8）を出す。

### 4.2 古い応答を出さない（PR-A / PR-B と同じ仕組み）

- 読み直しに番号を振り（`serverStatusRequests` / `FirewallStatusRequests` と同じ形）、適用の開始・新しい読み直しで
  古い番号を無効にする。応答の `generation` が**表示中の snapshot と一致するときだけ**表示する。ホストの方が
  新しければ `server_status` を読み直してから確認し直す。
- 発行の応答も同じ: 発行を押してから応答が来るまでに適用が始まったら、その応答（QR）は出さない。
- 適用中は「別の端末から確認」を押せない。

### 4.3 端末側（`/reach` ページ）

- SvelteKit の `(app)` の外のルート（`login` と同じ階層）。ログインの guard を通らない。
- フラグメントを読んで消し、POST して結果を出すだけ。ナビゲーション・ログインへの誘導・アプリの中身は出さない。
- フラグメントが無い・形が違う → 送らずに「使えない URL です」。

## 5. API の形の案

### 5.1 管理者用（Tauri IPC、admin のみ）

| コマンド | 認可 | verify:architecture | 内容 |
| --- | --- | --- | --- |
| `reach_check_issue({ host })` | `require_role(Admin, "settings")` | `DESKTOP_ONLY` | `host` は `live` の URL の候補から選んだもの（候補に無ければ拒否）。ロックの中で `generation`・`live` を読み、トークンを発行。応答 `{ generation, issueId, url, qrSvg, expiresInMs }` |
| `reach_check_status()` | `require_role(Admin, "settings")` | `TAURI_READ` | 応答 `{ generation, pending: { issueId, expiresInMs, host } \| null, selfAccessAt: number \| null, records: [{ issueId, at, peerIp, host, port }] }`（コードと値だけ） |

- `reach_check_issue` は永続する状態を変えないが、トークンを作る操作なので read ではなく desktop-only に分類する
  （REST に同等の口を作らない: 発行できるのはこの PC の管理者の画面だけ。ブラウザ配信の管理画面ではサーバの
  カード自体が出ない）。
- 未認証・viewer・editor は拒否し、**保管所に触れない**（トークンを作らない）。拒否の監査は conventions §1 の
  既存の `require_role` の扱いのまま（denied は認証済みでロール不足のときだけ）。
- `qrSvg` は既存の `qr_svg_for` で作る（`server_status` の `qr_svgs` と同じ。§7 の許可リストの既存の箇所で描く）。

### 5.2 LAN 面（REST）

| ルート | 認証 | verify:architecture | 内容 |
| --- | --- | --- | --- |
| `POST /api/reach-check` | なし（トークンを照合） | `REST_ONLY` | 本文 `{ token }`。§3.10 の応答 |

- **REST に変更系を足すことの扱い**: conventions §1 は mutating 操作の両経路の対称を求めるが、これは
  `POST /api/auth/grant/{kind}` と同じく「Tauri 側に対を持たないのが正しい」口になる。Tauri のウィンドウに
  「別の端末として到達する」という操作は存在せず、対の Tauri コマンドを作ると (C) の自己アクセスを確認として
  扱う誤りになる。`verify-architecture.mjs` の `REST_ONLY` に、その理由のコメントを付けて足す（grant と同じ
  書き方）。ロール床の照合（`ROLE_READ` / `DUAL_PATH` の `role`）の対象外。
- conventions §6 に、grant の項と並べて「到達確認の口」の規約（セッションを発行しない・トークンの条件・世代で失効・
  接続元はソケットだけ・監査しない・トークンを残さない）を足す。`rest/mod.rs` のモジュール doc の
  「`require_auth` の外のルート」の列挙と Route table にも足す（rule 8 (d) の doc-sync）。
- 置き場所は `banto-server` の新しいモジュール `reach_check.rs`（保管所 `ReachCheckState` とルーター
  `reach_check_router(state, generation, port)`）。派生アプリも同じ口を使える（D1）。`banto-serve` には発行する
  画面が無いので組み込まない（組み込んでも照合が必ず失敗するだけだが、未認証の口を増やさない方を採る）。

## 6. PR の分け方とテスト

### 6.1 PR の分け方（小さく）

1. **PR-C1: `banto-server` の保管所と口**（UI なし）。`reach_check.rs`（発行・照合・定数時間比較・期限・1 回限り・
   世代・このPC自身・`Host`・回数制限・記録の上限）、テンプレートの組み込みサーバーへの merge、`REST_ONLY` の分類、
   conventions §6・`rest/mod.rs` の doc。Rust のテストだけ。
2. **PR-C2: Tauri のコマンドと `server_apply` の失効**。`reach_check_issue` / `reach_check_status`、
   `server_apply` が世代を進めるときの失効、`TAURI_READ` / `DESKTOP_ONLY` の分類、`serverAdmin.ts` の型。
3. **PR-C3: 画面**。`/reach` ページ（i18n）と `LanReachCheckPanel`（QR・残り時間・読み直し・表示の分岐）、
   `docs/recipes/lan-access.md` の読み方、CHANGELOG。新しいルートを足すので
   `node scripts/scaffold.mjs --preset minimal|full|display --dry-run --strict` で scaffold の追従を確かめる。

各 PR で本書の `状態:` 行を更新する（AGENTS.md の寿命のルール）。

### 6.2 テストの方針

Rust（`banto-server`、`tower::oneshot` に `ConnectInfo` を差し込む）:

- 照合: 正しいトークンで `recorded`、記録の値（接続元 IP・ポート・世代・通し番号）が観測値どおり、
  応答にトークンが含まれない。
- 期限: 時計を差し替えられる形にし、期限の直前は通り、直後は `notFound`。
- 1 回限り: 2 回目は `notFound`。並行に 2 本送っても記録は 1 件（照合と使用済みは同じロックの中）。
- 世代: 保管所の世代を進めた後は発行済みのトークンが通らない・記録が消える。古い世代のルーターに届いた要求は
  通らない。世代を読んだ後に失効が挟まった発行は入らない（grant の世代のテストと同じ形）。
- このPC自身: loopback・IPv4 射影の loopback・インターフェースのアドレスからは `selfAccess` で、トークンは
  消費されず、その後の別の IP からは `recorded`。接続元が無ければ拒否。
- `Host`: 違うホスト・違うポートは `hostMismatch` で消費しない。
- 回数制限: 失敗 10 回の後は照合せずに 429、時間が経つと戻る、成功は数えない、IP の表の上限。
- 定数時間の比較の関数そのもの（長さ違い・1 バイト違い・一致）。
- 認可の外であること: 成功しても `/api/items/list` 等は 401 のまま、`X-Banto-Client` が無ければ 403、
  閲覧公開のオン / オフで結果が変わらない。
- 未使用の状態で `POST` しても記録が増えない（トークン無しの (B) の否定）。

Rust（`src-tauri`、`lib.rs` のテスト）:

- `reach_check_issue` / `reach_check_status` は未認証・viewer・editor を拒否し、保管所に触れない。
- 停止中・loopback のみ・IPv6 では発行しない。`host` が `live` の候補に無ければ拒否する。
- 発行 → `server_apply` → 古いトークンは通らない・結果は消える・`generation` が進む。
- 応答が camelCase の JSON。

vitest:

- 表示の分岐（§4.1 の表の全状態）、古い応答の破棄（「A を保留 → 適用 → A を解放」で A を出さない）、
  `generation` の不一致・ホストが新しいときの読み直し、読めないときに「未確認」にしないこと。
- `/reach` ページ: フラグメントの読み取りと `replaceState`、フラグメントが無いときに送らないこと、応答ごとの文言。

e2e:

- `tauri-settings-drafts.spec.ts` の Issue #219 のシナリオに、IPC をスタブにした欄の表示（確認待ち → 確認済み、
  待受の変化で未確認に戻る）。
- ブラウザ配信で `/reach#t=…` を開き、POST の本文とヘッダー、URL からフラグメントが消えることを確かめる
  （`/api/reach-check` はスタブ）。

実機（手で、PR-C3 の完了条件）: 同じ Wi-Fi のスマートフォンで QR を読み取って確認済みになること、同じ PC の
ブラウザで開くと「このPC自身」になること、ファイアウォールで遮断した状態では期限切れになること、
ポートを変えると結果が消えること。検証した OS・端末を PR に書く。

## 7. 判断が要る点（D1〜D10）

| 論点 | 推奨 |
| --- | --- |
| D1 保管所と口の置き場所 | **a: `banto-server` のモジュール**（派生アプリも使える） |
| D2 端末側のページの作り方 | **a: SPA の `/reach` ＋フラグメント＋ POST** |
| D3 トークンの長さ | **a: `uuid` v4 1 つ（122 ビット）** |
| D4 有効期限 | **b: 5 分** |
| D5 同時に有効なトークンの数 | **a: 1 つ（新しい発行で前のものを失効）** |
| D6 回数制限 | **a: 接続元 IP ごとに失敗 10 回／分、表は 256 件まで** |
| D7 「どの NIC に届いたか」の記録 | **a: 記録しない（`Host` の一致だけ。保証しないことに書く）** |
| D8 監査 | **a: 発行も到達も監査しない** |
| D9 管理者の画面の更新の仕方 | **a: 確認待ちの間だけ 2 秒おきに読み直す** |
| D10 「古い」と出すまでの時間 | **b: 1 時間** |

### D1. 保管所と口の置き場所

- **a（推奨）**: `banto-server` に `reach_check.rs` を置き、テンプレートの組み込みサーバーで merge する。grant と同じく
  派生アプリが同じ規約の口をそのまま使え、conventions §6 の規約も 1 か所で済む。
- b: アプリの crate（`admin-template-core` の `rest/`）に置く。派生アプリはコピーして持つことになり、安全の規約の
  レビューが散らばる。

### D2. 端末側のページの作り方

- **a（推奨）**: SPA の `/reach` ページがフラグメントのトークンを POST する。トークンがログ・`Referer` に残らず、
  プレビュー・先読みで消費されず、文言は Paraglide（§13 の例外を作らない）。端末で JavaScript が要るが、SPA は
  元々 JavaScript が要る。
- b: GET `/reach?t=…` にサーバーが短い HTML を返して記録する。JavaScript が要らないが、トークンがクエリに乗り、
  リンクのプレビューで消費され、GET で状態を変え、Rust に文言（または言語ごとの HTML）を持つことになる。採らない。

### D3. トークンの長さ

- **a（推奨）**: `uuid` v4 1 つ（122 ビット）。セッションのトークンと同じ強さで、5 分・1 回限り・回数制限の下では
  十分。QR も小さく保てる。
- b: v4 を 2 つ連結（244 ビット）。余裕は増えるが QR が細かくなり、読み取りにくくなる。

### D4. 有効期限

- a: 2 分。漏れたときの窓は狭いが、端末の準備（Wi-Fi に入る、カメラを起動する）で切れやすい。
- **b（推奨）**: 5 分。
- c: 10 分。

### D5. 同時に有効なトークンの数

- **a（推奨）**: 1 つ。画面の QR と生きているトークンが常に 1 対 1 で、照合のなめる数も 1。
- b: 少数（例 4）。複数の端末で同時に確かめられるが、画面に複数の QR の状態を出す必要がある。続けて確認すれば
  a でも複数の端末の記録は残る（§4.1）。

### D6. 回数制限

- **a（推奨）**: 失敗した照合に、接続元 IP ごとの回数制限（10 回／分で 1 分止める、IP の表は 256 件で古いものから
  捨てる）。軽い自前の実装（ログインの `RateLimitPolicy` は argon2 の前の枠の予約まで含むので流用しない）。
- b: 回数制限を付けない（122 ビットと 1 回限りで総当たりは成り立たない）。実装は減るが、未認証の口に制限が無い
  例外を作ることになる。
- c: ログインの `RateLimitPolicy` を一般化して共用する。ログインの規約（§6「重い検証の前にスロットル」）の
  コードに手を入れることになり、この PR の範囲を超える。

### D7. 「どの NIC に届いたか」の記録

- **a（推奨）**: 記録しない。`Host` が発行時のホストと一致したことと、サーバー側のポートだけを記録し、
  「届いた NIC の証明ではない」と書く。`0.0.0.0` で待ち受けるときに問題になるが、端末は発行した URL の IP へ
  つないだのが普通なので、実用上は足りる。
- b: 接続ごとのローカルアドレスを取る。`BoundServer::serve` の `into_make_service_with_connect_info::<SocketAddr>()`
  を接続元とローカルの両方を持つ型に変える必要があり、`ConnectInfo<SocketAddr>` を読む既存の箇所
  （`MaybePeerAddr`・`request_from_loopback_peer`・`request_is_loopback_local`・grant）と派生アプリの公開 API に
  影響する。別の Issue として扱う。

### D8. 監査

- **a（推奨）**: 発行も到達も監査しない（§3.9）。
- b: 発行だけ監査する（admin の操作で数が少なく、増幅しない）。永続する状態を変えない操作を監査に載せる前例を
  作ることになる。
- c: 到達も監査する。資格情報なしの口で監査を増やすので、Issue #278 の規約に反する。採らない。

### D9. 管理者の画面の更新の仕方

- **a（推奨）**: 確認待ちの間だけ、`reach_check_status` を 2 秒おきに読み直す（メモリを読むだけで軽い）。
  期限切れ・確認済みで止める。
- b: サーバーの照合から Tauri のイベントを出す。即時だが、`banto-server` のモジュールから Tauri の `AppHandle` へ
  知らせる経路（コールバック）が要り、層の境界（conventions §2 の精神）をまたぐ。

### D10. 「古い」と出すまでの時間

- a: 10 分。
- **b（推奨）**: 1 時間。確認の直後に設定を詰める作業の間は「確認済み」のまま、翌日に見たときは古いと分かる。
- c: 時間では古くしない（待受が変わったときだけ捨てる）。「その時点」の確認であることが伝わりにくい。

### そのほか（推奨どおりなら判断不要）

- ADR は書かない: 認証の仕組み（grant・セッション）を変えず、未認証の口の規約は conventions §6 に足す。
  もし D1 を b にする・D7 を b にする場合は、公開 API に触れるので ADR を検討する。
