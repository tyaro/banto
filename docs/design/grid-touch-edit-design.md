## 1. 目的と範囲

タッチだけの端末で、`@banto/grid-svelte` のセルを **1 回のタップ → 盤で入力 → 盤の「確定」** で書き換えられるようにする。
今は 2 つ足りない（touch-keypad-design §6.4）。

1. **編集の開始がダブルクリックだけ**（`BantoGrid.svelte` の `handleCellDoubleClick`。キーボードは Enter / F2）。
2. **盤の「確定」ではセルが確定しない**。盤は入力欄へ書いて `input`・`change` を出す所までで（`TouchKeysHost.svelte` の `confirm`）、
   セルの確定は blur（`handleEditorBlur`）か Enter / Tab（`handleEditorKeydown`）を待つ。

同じ根の問題が forms にある: `DraftNumberField` は `input` では `draft.setRaw()` しか呼ばず、確定は blur か Enter の `draft.commit()`（§7）。

**範囲外**: 盤そのもの（T1〜T5 で済み）、admin-template への盤の配線（T7）、チェックボックス・選択肢のセルを 1 回のタップで切り替えること
（今と同じく、編集に入ってからもう 1 度タップする）、編集できるセルの見た目の手がかり、実機の確かめ（touch-keypad-design §14.4）。

## 2. 今の実装（読んで確かめたこと）

- **セルのイベント**（`BantoGrid.svelte` のセルの `div`）: `onpointerdown`（`handleCellPointerDown`）・`onclick`（`handleCellClick`）・
  `oncontextmenu`（`handleCellContextMenu`）・`ondblclick`（`handleCellDoubleClick`）。
  - `pointerdown`（左ボタン）: コンテナへ `focus({ preventScroll: true })` し（これが編集中の別のセルを blur させて確定する）、
    `selection.setActive` でアクティブセルを動かす。その後 window の `pointermove` で範囲選択を伸ばし、`pointerup` で外す。
    **`pointerType` は見ていない。`pointercancel` は聞いていない。**
  - `click`: 編集できる列が 1 つも無い grid だけ `onRowClick` を呼ぶ。編集できる列がある grid では何もしない。
  - `dblclick`: 編集できるセルなら `startEditing`、そうでなく編集できる列がある grid なら `onRowClick`。
  - `contextmenu`: `onRowContextMenu` があれば既定のメニューを止めて呼ぶ（エディタの中は素通し）。
- **`EditController`**（`edit.svelte.ts`、非公開）: `start(column, row)` が、開いているセッションを置き換えて新しいセッションを作る。
  列は持たない。フォーカスの持ち主（#212）を `ownsFocus` で持つ。
- **フォーカスの持ち主を手放す所**（`BantoGrid.svelte` の `relinquishFocus`）: document の捕捉の `pointerdown` が、
  **エディタの外の押下なら、実際のフォーカスが入力欄に残っていても**手放す（`setFocusOwned(false)`）。取り直すのは、
  エディタへの `focusin` と、フォーカス中のエディタでの `keydown`（`renewFocus`）だけ。
  **盤はエディタの外にあるので、盤のキーを押した時点で手放される**（盤が DOM のフォーカスを動かさなくても、持ち主は別の話）。
- **エディタ**（`CellEditor.svelte`）: 文字は `<input type="text">`、**数値は `<input type="number">`**（`min` / `max` は付けない）、
  選択肢は `<select>`、真偽は checkbox、日付・時刻は注入したエディタか素の入力欄。エディタの `pointerdown` は伝播を止めている。
  新しいエディタには、セッションがフォーカスを持つ間だけ `$effect` が `focus()` と `select()` をする。
- **確定**（`commitFromEditor`）: blur は移動なし、Enter は下へ、Tab は右（Shift で左）へ動き、動くときだけコンテナへフォーカスを戻す。
  blur の確定で閉じたときは、フォーカスを戻さない。
- **盤**（`TouchKeysHost.svelte`）: document の `pointerdown`（捕捉）で対象の入力欄の OS のキーボードを抑え、`click`（捕捉）で
  **クリックされた要素そのものが対象の入力欄のとき**だけ開く。フォーカスが入っただけでは開かない。
  確定は「閉じる → `input` → `change` → `onconfirm`」の順で、フォーカスは入力欄に残る。取り消しは何も出さない。

### 2.1 タッチで起きていること（コードの読み。未確認）

- **スクロールの始まりでも選択と確定が動く**: 指を置いた時点の `pointerdown` でアクティブセルが動き、編集中のセルがあれば blur で確定する。
  ブラウザーがスクロールと決めるまでの `pointermove` で、範囲選択が数セル伸びることがある。
- **window のリスナーが残る**: スクロールになるとブラウザーは `pointerup` でなく `pointercancel` を出すので、`pointermove`・`pointerup` の
  リスナーが外れない（`pointerId` で絞っているので誤動作はしないが、スクロールのたびに 2 つずつ増える）。
- **編集中の入力欄の中のダブルクリックが、セルの `dblclick` に届く**: 素の入力欄は `dblclick` の伝播を止めていない
  （止めているのは注入したエディタの包みとリンクだけ）。`start` は同じセルでも作り直すので、下書きが元の値に戻る見込み。
  タップで始めた直後の 2 回目のタップ（ダブルタップ）でも同じ経路を通る。G1 で試験を足して確かめる。

## 3. タップの判定

### 3.1 何をタップとするか

**ブラウザーの `click` を使い、その `click` を生んだ `pointerdown` の `pointerType` が `touch` か `pen` のときをタップとする。**
時間や移動量を自前で測らない。

| 区別したいもの | どう区別されるか |
| --- | --- |
| スクロール（パン） | ブラウザーが `pointercancel` を出し、`click` を出さない。grid は何もしない |
| 長押し | `contextmenu` が出て `click` は出ない（Chromium / WebView2。未確認）。今の `handleCellContextMenu` がそのまま働く |
| マウス | `pointerType` が `mouse`。**今のまま**（1 回のクリックは選択だけ、ダブルクリックで編集） |
| キーボード・支援技術が合成した `click` | 直前に `touch` / `pen` の `pointerdown` が無いので、マウスと同じ扱い |

`pointerType` はセルの `pointerdown` で控える（`click` が `PointerEvent` でないブラウザーと jsdom でも同じ経路になる）。
控えは次の `click`・`pointercancel`・別の `pointerdown` で捨てる。

**マウスの 1 回のクリックで編集を始める形にはしない。** クリックは範囲選択の起点で、表計算と同じ「選ぶ → ダブルクリックか Enter で編集」を
保つ。タッチには範囲選択のドラッグが無い（ドラッグはスクロール）ので、タップを編集に使っても失うものが無い。

### 3.2 タッチ・ペンのときの `pointerdown`

タッチ・ペンでは、**`pointerdown` では何もしない**（`pointerType` を控えるだけ）。フォーカス・アクティブセルの移動・編集の開始は、
`click` でまとめて行う。これで、スクロールの始まりで選択が動く・編集中のセルが確定する・範囲が伸びる（§2.1）が無くなる。
window の `pointermove`・`pointerup` のリスナーはマウスのときだけ付け、`pointercancel` でも外す。

### 3.3 タップで起きること

| タップした場所 | 起きること |
| --- | --- |
| 編集できるセル | コンテナへフォーカス（編集中の別のセルは blur で確定）→ アクティブセルを動かす → `startEditing` |
| 編集中のセル自身・そのエディタの中 | 何もしない（エディタの中のタップは入力欄のもの。盤は入力欄のタップで開く）。`dblclick` でも作り直さない |
| 編集できないセル（編集できる列がある grid） | 選択だけ。**`onRowClick` は呼ばない**（今のクリックと同じ。行を開く口はリンクの列）|
| 編集できる列が無い grid のセル | 今と同じ（`onRowClick`） |
| 行の選択の列・グループの見出し・リンク | 今と同じ |
| 長押し | `onRowContextMenu`（あれば）。編集は始めない |

保存中（`pending`）のセルへのタップは、今のダブルクリックと同じ（`start` が新しいセッションを作り、前の保存の結果は前のセッションのもの）。

### 3.4 切り替え

`BantoGrid` に props を 1 つ足す（見込み: `editOnTap?: boolean`、**既定 `true`**）。`false` なら今のまま（タッチもダブルタップ）。
既定を `true` にするのは、タッチではそれ以外に実用的な始め方が無いため（§11 の 1）。`EditController` は変えない
（始め方が増えるだけで、セッションの形は同じ）。

## 4. 盤との繋ぎ方

### 4.1 境界

**grid は touch-keys を知らない。touch-keys も grid を知らない。繋ぐのはアプリの 1 か所（`TouchKeysHost` を置いているルート）。**
conventions §4 は import を機械で見るが、名前だけの結びつき（grid が `data-touch-keys-*` を出すなど）も作らない。

| 側 | 足すもの（どれも相手の名前を持たない） |
| --- | --- |
| grid（コア） | ① タップで編集を始める（§3）。② セルのエディタに印の属性（**G2 で決めた形: `data-grid-editor`**。組み込みのエディタは要素自身、注入したエディタは包みに付く）を付け、公開の約束にする。③ フォーカス中のエディタに届いた `input` でフォーカスの持ち主を取り直し、持ったままの blur で確定して閉じたら、フォーカスをコンテナへ戻す（§5.1） |
| touch-keys（オプション） | ④ 「ページのコードが、クリックの結果として入力欄へフォーカスを移したときも開く」を、入力欄ごとに選べるようにする（§4.2） |
| アプリ（テンプレートとレシピ） | ⑤ ルートで、②の印が付いた入力欄に ④ を有効にし、`onconfirm` でその入力欄を blur する（§5.1） |

### 4.2 1 回のタップで編集と盤を始める

タップの `click` の宛先はセルで、入力欄はその後に作られてフォーカスを受ける。今の盤は「クリックされた要素が入力欄」のときだけ開くので、
**何も足さないと 2 回のタップになる**（1 回目で編集、2 回目に入力欄をタップして盤）。しかも 1 回目のフォーカスでは盤が
OS のキーボードを抑えていない（抑えるのは入力欄の `pointerdown`）ので、端末によっては OS のキーボードが出る。

| 案 | 中身 | 評価 |
| --- | --- | --- |
| **A（推奨）** | touch-keys に、入力欄ごとのオプション（見込み: `openOnFocus`）を足す。`click` の処理の続き（同じタスクの中）で、そのオプションを持つ対象の入力欄へフォーカスが入ったら、OS のキーボードを抑えて開く。アプリが `resolve` で ②の印の入力欄に付ける | 既定の挙動は変わらない。grid 以外（ボタンを押すと入力欄が現れる画面）にも使える。ルートの 1 か所で全部の grid に効く |
| B | grid が、タップで始めた直後にエディタへ `click()` を送る | 配線が要らないが、合成の `click` が祖先のアプリのハンドラーにも届く。checkbox は反転してしまう。理由が grid のコードから読めない |
| C | grid に `onEditStart` のコールバック、盤に命令の `open(input)` を足し、grid ごとにアプリが繋ぐ | grid を置くたびに配線が要る。書き忘れると黙って 2 回タップになる |
| D | 何も足さない（2 回タップ） | OS のキーボードが出うる。Issue の「タップで入力」に届かない |
| E | 盤が、フォーカスが入っただけで常に開く | 入力欄に自動でフォーカスするダイアログ・検索でも開く。T2 の決定（タップで開く）を全体で変えることになる |

A の細かい形は K1 で決める: `resolve` は今 `kind` つきの指定を返すので、**推定はそのままにしてオプションだけ足す返し方**が要る。
「クリックの続き」の範囲（同じタスクまでか、短い猶予を持つか）、キーボードの Enter が合成した `click` を数えるか、も K1 で決める。
マウスのダブルクリックで始めた編集でも、盤が有効な端末なら同じ規則で開く（Enter / F2 で始めた編集では開かない）。

**OS のキーボード（未確認）**: A では、抑えるのがフォーカスの後になる。フォーカス中に `inputmode` を変えて OS のキーボードが
出ずに済むかは、実機で確かめる（touch-keypad-design §14.4 に 1 行足す）。一瞬出る端末があれば、K1 で対処を決める。

### 4.3 盤が開く入力欄

- 数値の列（`type="number"`）はテンキー、文字の列は文字キーボード（盤の推定のまま）。
  **数値の範囲は付かない**（grid の数値のエディタは `min` / `max` を DOM に出さない）。範囲は列の `validate` が確定のときに見る。
  範囲を DOM に出すかは、この設計の外（要るなら別の Issue）。
- 日付・時刻の列は、レシピのとおり包みに `data-touch-keys="off"`（アプリの注入するエディタの側。今のまま）。
- `<select>`・checkbox は盤の対象でない。

## 5. 確定・取り消し・次のセル

### 5.1 確定

盤の確定の後、**アプリが `onconfirm` でその入力欄を `blur()` する**（②の印の入力欄だけ）。セルは今の blur の経路
（`handleEditorBlur` → `commitFromEditor`、移動なし）で確定する。順は「盤が閉じる → `input`（grid が下書きを受ける）→ `change` →
`onconfirm` → blur → 確定」。

| 案 | 中身 | 評価 |
| --- | --- | --- |
| **A（推奨）** | 印の入力欄だけ、確定の後に blur する（アプリの `onconfirm`。新しい API なし） | 今ある、試験済みの確定の経路をそのまま使う。grid に新しい確定の口を作らない |
| B | grid がエディタの `change` で確定する | 数値のエディタは `type="number"` で、スピンの操作でも `change` が出うる（未確認）。マウスの利用者の編集が 1 段で閉じる恐れ |
| C | `isTrusted` が false の `change` だけを盤の確定とみなす | 試験の合成イベントと区別できない。イベントの出どころで意味を変えない（touch-keypad-design §6.3 と同じ考え） |
| D | grid に公開の `commitEdit()` を足し、grid ごとにアプリが呼ぶ | grid ごとの配線。どの grid の入力欄かをアプリが引く必要がある |
| E | 盤が、確定の後に常に blur する | フォーカスが外れると閉じるポップアップ（フィルター・コマンドパレット）の中の入力欄で、盤の確定がポップアップを閉じる恐れ |

**フォーカスの持ち主の取り直し（grid の ③ の前提）**: 盤のキーの押下はエディタの外の `pointerdown` なので、今の grid は
持ち主を手放す（§2）。そのままでは、下の「戻す」も「失敗したときにエディタへ戻る」も働かない。そこで grid に規則を 1 つ足す（G2 で実装。`BantoGrid.svelte` の `handleEditorInput`）:
**いまのセッションのエディタ自身に `input` が届き、その時点で実際のフォーカスがそのエディタにあり、保存待ちでないなら、
持ち主を取り直す**（`renewFocus(sessionId)`。フォーカス中のエディタの `keydown` で取り直す今の規則と同じ形）。
盤の確定は、フォーカスが残ったままの入力欄へ `input` を出すので、この規則に当たる。grid は盤を知らないまま
（フォーカスを動かさずに入力欄へ書く物なら、何でも同じ）。

- 取り直すのは **その入力欄・そのセッションだけ**。`input` が届かない操作（盤の取り消し・盤の外の押下）では取り直さない。
- 押下でフォーカスが実際にエディタから離れたとき（フォーカスできない所のクリックも含む）は、`input` が届かないので手放したまま。
- **保存待ちの間に別の場所を操作したら、そちらが勝つ**: 確定の後の `pointerdown` は今までどおり手放し、保存が終わっても
  （成功でも失敗でも）フォーカスを取り返さない。

**blur の後のフォーカス（grid の ③）**: プログラムの blur ではフォーカスが `body` に落ちる。セッションがフォーカスを持ったまま
（`ownsFocus`。上の取り直しの後、外の押下やフォーカスの移動で手放していない）blur の確定で閉じ、**閉じた時点でも**持ち主のままで
フォーカスが `body` にあるときは、コンテナへ戻す（G2 で実装。`commitFromEditor` の移動なしの枝。ウィンドウ自体が
フォーカスを失っている間（`document.hasFocus()` が false）は戻さない）。アクティブセルは編集したセルのまま。利用者が別の場所へ移った blur（今の経路）は、
今までどおり戻さない（#212）。

**確定に失敗したとき**（検証の失敗・保存の拒否）: セッションは開いたまま、下書きを残してエラーが出る。持ち主のままなら、今の `$effect` が
エディタへフォーカスを戻す。入力欄をタップすれば、盤がいまの下書きで開く。保存中（`pending`）は今と同じく入力を受けない。

### 5.2 取り消し

**盤の取り消しのキーと外のタップは、盤を閉じるだけ。セルの編集は開いたまま**（盤を開く前の状態に戻る）。
盤は取り消しで何も書かないので、下書きは盤を開く前のまま。その後は、別の場所のタップ（blur の確定。変えていなければ何も保存しない）か、
実キーボードの Esc で編集を閉じる。取り消しでセルの編集まで閉じる形（取り消しでも blur する）は採らない: 実キーボードで打った下書きが
あると、「取り消し」を押したのに確定されるため。

**実キーボードの Esc は別**（今の実装のまま、調停は変えない）: 盤が開いていてもフォーカスはセルのエディタにあるので、Esc は先に
`handleEditorKeydown` に届く。grid は `preventDefault` と `stopPropagation` をして編集を取り消し、エディタが消える。
盤の Esc の処理（window のバブル。`defaultPrevented` なら譲る）には届かず、盤は対象が消えたことで閉じる（`target-gone`）。
つまり **Esc 1 回で、セルの編集と盤の両方が閉じ、値は変わらない**。touch-keypad-design §7.3 の「Esc を消費した入力欄が勝つ」の
とおりで、grid の Esc（編集の取り消し）の意味も変わらない。

「Esc は盤だけを閉じ、セルの編集は残す」にするには、grid が「盤が開いている」ことを知って Esc を譲るか、盤が捕捉の段で
Esc を先に取る（T2 で決めた層の調停を変える）必要がある。前者は境界（§4.1）を崩し、後者は grid 以外の入力欄・層にも効くので、
採らない（§11 の 9）。

### 5.3 次のセルへの移動

**盤の確定では動かない**（blur の確定と同じ。アクティブセルは編集したセルに残る）。次のセルは次のタップで始める。
実キーボードの Enter（下へ）・Tab（右へ）は今のまま。

「確定したら下のセルの編集と盤を続けて開く」（連続入力）は、この設計に入れない。要る画面が出たら、列か grid のオプションとして
別に決める（§11 の 5）。

### 5.4 盤が開いている間

- 行が消える・仮想スクロールで外れる・列が編集できなくなる → grid が編集を取り消してエディタが消え、盤は `target-gone` で閉じる（今の盤の規則）。
- 盤の受け面が外のタップを受けるので、盤が開いている間に別のセルのタップは届かない（1 回目は盤を閉じるだけ）。
- 同じセルを開き直しても、エディタの `<input>` は作り直される（セルごとの `{#if}`）。盤の照合（`editKey`）は要らない見込み。G1 で確かめる。

## 7. `DraftNumberField`（forms）

**T6 の範囲に含める。ただし PR は grid と分ける（F1）。** 根は同じ（盤の確定が「値の確定」として届かない）だが、直し方は違う。

- `DraftNumberField` は `<input type="text" inputmode="decimal">` で、`type="text"` の `change` は「利用者が値を確定した」とき
  （blur・Enter）にしか出ない。どちらも今 `draft.commit()` を呼んでいる。そこで **`onchange` でも `draft.commit()` を呼ぶ**（1 行）。
  盤の確定の `change` で確定と検証が走り、レシピの「限界」が消える。素の操作では、今の確定の直前にもう 1 度呼ばれるだけ
  （`FormDraft.commit` は、未確定の文字が無ければ検証だけをする）。
- grid で同じ形（`change` で確定）を採らないのは、数値のエディタが `type="number"` だから（§5.1 の B）。
- forms は touch-keys を知らないまま（`change` は DOM の標準の意味で使う）。アプリの配線も要らない。
- `DraftDateField` など、下書きを持つほかの欄に同じ穴があるかは F1 で確かめる（日付の欄はレシピで盤の対象から外している）。

別の Issue に分ける案もあるが、1 行で済み、次のリリースのレシピから限界の記述を消せるので、T6 と一緒に出す（§11 の 6）。

## 8. a11y

- キーボードの経路（Enter / F2 で編集、Enter / Tab で確定、Esc で取り消し）は変えない。タップはポインターの経路が増えるだけ。
- スクリーンリーダーのタッチ操作が合成する `click` は、`touch` の `pointerdown` を伴わなければマウスと同じ（選択だけ）で、
  編集は今と同じく Enter から。支援技術ごとの違いは未確認。
- 確定の後にフォーカスをコンテナへ戻す（§5.1）ので、盤の後も矢印キーと読み上げの位置がセルに残る。
- エディタの名前（列の見出しの `aria-label`）・エラーの領域（`CellEditError`）は今のまま。盤の a11y は touch-keypad-design §13。
- タップの的はセル全体（タッチの密度で行 52px）。長押しに頼る操作は足さない（`onRowContextMenu` は今もキーボードの口がある）。

## 9. 試験と e2e の方針

touch-keypad-design §14 と同じく、jsdom が持たないもの（当たり判定・スクロールの判定・本物のフォーカス）は jsdom の試験に書かない。

| 場所 | 確かめること |
| --- | --- |
| grid の部品の試験（jsdom、`packages/grid-svelte/tests/`） | `pointerType: 'touch'` / `'pen'` の `pointerdown` + `click` で編集が始まる／マウスの `click` では始まらない／`pointercancel` の後は始まらず、選択も動かず、window のリスナーが残らない／`contextmenu` では始まらず `onRowContextMenu` が呼ばれる／編集中のセルの `click`・`dblclick` で下書きが戻らない／編集できないセル・`editOnTap={false}`／印の属性／フォーカスを持ったままの blur の確定でコンテナへ戻り、手放した blur では戻らない／**持ち主の取り直し**: エディタの外の `pointerdown`（フォーカスは残る）→ エディタへ `input` で取り直す・`input` が無ければ手放したまま・フォーカスが離れていれば取り直さない・保存待ちでは取り直さない |
| touch-keys の部品の試験と fixture（`packages/touch-keys-svelte/tests/`） | `openOnFocus` の入力欄: クリックの続きのフォーカスで開く／オプションなしでは開かない／キーボードだけのフォーカスでは開かない。fixture（`hasTouch: true`）に「ボタンをタップすると入力欄が現れてフォーカスを受ける」画面を足す |
| forms の試験 | `DraftNumberField`: `input` + `change` で `commit` が走り、検証のエラーが出る／blur・Enter と重なっても 2 重に壊れない |
| 組み合わせの e2e（ルートの `e2e/`、admin-template の `/ui-demo` の編集できる grid） | タッチの文脈（`hasTouch: true`、`locator.tap()`）で: セルを 1 回タップ → 盤が開く → 数字 → 確定 → セルの表示が変わり、エディタが消え、**元のセルがアクティブのまま**フォーカスが grid にある（**盤のキーを実際にタップして**確かめる）／**保存の拒否**: 下書きが残り、エラーが出て、フォーカスが入力欄に戻る／**保存待ちの間に別の場所を操作**: 保存が終わってもフォーカスはそちらに残る／盤の取り消しのキーでは値が変わらず、編集は開いたまま／**盤が開いている間の実キーボードの Esc**: 1 回で盤とエディタの両方が消え、値は変わらず、フォーカスが grid にある／マウスの 1 回のクリックでは編集が始まらない |
| 実機（touch-keypad-design §14.4 に足す） | スクロールの始まりで編集が始まらない・選択が動かない／長押し／1 回のタップで OS のキーボードが出ない |

- **スクロールとの区別**は、Playwright の `touchscreen.tap()` では再現できない。単体では `pointercancel` の経路を確かめ、
  本物のパンは実機の項目にする（CDP の合成ジェスチャーを使うかは G1 で決める。不安定なら入れない）。
- 組み合わせの e2e を admin-template に置くのは、T7 が `/ui-demo` に盤を配線するため。touch-keys の fixture に grid を足す案は採らない
  （fixture は盤だけの最小の画面のままにする。CI の実行の条件も変えずに済む）。
- 基準画像は変わらない見込み（見た目を変えない）。

### 10.1 W1 で決めた形

- **配線の置き場は `/ui-demo` の TouchKeysHost のカード**（ルートのレイアウトではない）。T7 が「テンプレートのホストは見本のカードの中の
  1 つだけ」と決めた（touch-keypad-design §4.2 の b・§15.4）ので、§4.1 の ⑤ の「ルート」は、テンプレートではそのカードのホストを指す。
  カードに編集できる grid（数量 = 数値、ロット = 文字）を足し、そのホストの `resolve` が `data-grid-editor` の欄に
  `{ openOnFocus: true }` を返し、`onconfirm` がその欄だけを `blur()` する。ルートに 2 つ目のホストは置かない
  （2 つあると盤が 2 つ開く）。アプリがルートに置くときの形は、レシピ「grid のセル」に書いた。
- **scaffold**: grid の見本・配線は `[scaffold:touch-keys]` の 2 領域の中に収めたので、`removeTouchKeys` の印の数は変わらない。
  足したのは e2e の削除 1 行（`e2e/demo/touch-keys-grid.spec.ts`）。文言は `uiDemo.touchKeys.*` の下で、今の remover が消す。
- **組み合わせの e2e** は `e2e/demo/touch-keys-grid.spec.ts`（`demo` の project。`hasTouch: true`、盤のキーも `tap()`）:
  マウスの 1 回のクリックでは始まらない／1 回のタップで編集と盤／確定でセルが確定し、元のセルがアクティブのまま grid にフォーカス／
  保存の拒否（見本の数量は在庫 500 を超えると保存が失敗する）で下書きとエラーが残り、フォーカスがエディタに戻り、タップで盤が開き直す／
  盤の取り消しでは編集が開いたまま／実キーボードの Esc 1 回で両方が閉じる／保存待ち（見本のロットは保存が少し遅い）の間に
  別の場所をタップしたら、フォーカスはそちらに残る。ハイドレーション待ちの再試行は grid でなくカードの素の欄で行う
  （セルのタップを再試行すると、「1 回目で編集だけ始まり、2 回目で盤が開く」退行を見逃すため）。
  **本物の `TouchKeysHost` で `openOnFocus` の窓が足りる**ことは、この e2e で確かめた（Chromium、3 回続けて緑）。
- **forms のほかの欄**（§7 の残り）: `TextField`・`NumberField`・`PasswordField`・`TextareaField`・`DateField`・`ReferenceField` は
  `input` で `FormStore` に値が入るので、F1 と同じ穴は無い（`<textarea>` と `type="date"` などはそもそも盤の対象でない）。
  `DraftDateField` は、注入した日付の入力欄（文字の欄）に盤で書くと `input` → `setRaw` までで、確定は blur・Enter を待つ
  （F1 と同じ形の穴）。ただし日付・時刻の欄は、レシピで盤の対象から外す（`data-touch-keys="off"`）と決めているので、直さない。
  直すなら、注入する入力欄の約束（`onTextInput`・`onValueChange`・`onblur`・`onkeydown`）に `change` を足すことになり、
  `@banto/ui` の `DateInput` と date-time-pickers §5 の約束に触る（要る画面が出たら別の Issue）。
- **基準画像**: カードが高くなるので、`ui-demo` の系統だけ `visual-baselines.yml` で作り直した（§9 の「変わらない見込み」は、
  見本を足したので当たらなかった。パッケージの見た目は変えていない）。

## 12. 危うい点

- **フォーカスの後に OS のキーボードを抑える**（§4.2）: 端末によって一瞬出るかもしれない。実機でしか分からない。
- **「クリックの続き」の判定**（K1）: 短すぎると開かず、長すぎると関係の無いフォーカスで開く。fixture で本物のブラウザーの順を確かめる。
- **長押しの `contextmenu`**・**ペンのドラッグがスクロールになるか**は、ブラウザーと OS の設定で違う。WebView2 と Chromium 以外は未確認。
- **既定の変更**（§11 の 1）: タッチの端末で、タップの意味が「選ぶ」から「編集を始める」に変わる。CHANGELOG の「消費側への注意」に書く。
- **#212 のフォーカスの規則**（G2）: 「手放したフォーカスは取り戻さない」を崩さない。取り直すのは、フォーカスが実際に残っている
  エディタへ `input` が届いたときだけ。戻すのは、持ったまま `body` に落ちたときだけ。盤のキーの押下で手放される（§2）ので、
  取り直しを入れずに ③ だけを実装すると、jsdom の試験（盤を通さない blur）は通るのに、実際の盤では戻らない。組み合わせの e2e で守る。
