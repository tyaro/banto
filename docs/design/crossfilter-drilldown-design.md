## 1. 用語

- **ドリルダウン**: チャートの棒・扇・点（以下「印」）から、該当するレコードの一覧（`/items` の絞り込み済みの表示）へ移る。
- **クロスフィルタ**: あるウィジェットで選んだ値（カテゴリ・価格帯）で、同じダッシュボードのほかのウィジェットを絞る。
- **次元**: 絞り込みに使える値の種類（例: `category`・`priceBucket`）。作者がコードで決める閉じた集合。

## 2. まず「要るか」の見直し

### 2.1 いま分かっていること

- **下流に、ダッシュボードのウィジェットの登録（`dashboardWidgets.ts`）を使っているアプリは見当たらない**。
  2026-11-24 に作業機の作業コピーを grep した範囲: banto-industrial の chronogazer は `@banto/charts` を監視画面の
  ゲージで使うだけ、banto-hub と temp-scada には `@banto/charts` の利用もウィジェットの登録も無い。
  下流の要望（2026-11-21〜22 の 9 件と追加の 4 件、downstream-requests-2026-11-plan §4）にも、クロスフィルタ・
  ドリルダウンは無い。出どころは洗練案（design-ux-review-2026-11 の D-1）だけ。
- **ダッシュボードはアプリの層のデモ**（template-scope §3 の表の外。`display` プリセットは `/dashboard` ごと消す）。
  派生アプリの作者が写して書き換える「型の見本」としての値打ちはあるが、パッケージの機能ではない。
- **ドリルダウンには、すでに見本と宿題がある**。KPI のタイル「在庫少」は `/items?view=low-stock` へ移る（#555）。
  ただし W3 の「残したこと」（§4.13.10）のとおり、タイルの件数は期間で絞るのに、移った先の一覧は期間で絞らない。
- **ドリルダウンの部品は、ダッシュボードの外でも使える**。「印を選べるチャート」と「引数つきの一覧のビュー」は、
  下流の監視・帳票の画面（例: パレート図の棒 → 該当のイベントの一覧）でもそのまま使える。
  クロスフィルタの部品（次元ごとの絞り込み・選択の帯）は、ダッシュボードの中でしか使わない。
- **費用**: ドリルダウンは基準画像が変わらない見込み（静止の見た目は同じ）。クロスフィルタは、選択の帯・選択中の印の
  見た目・絞り込みの組み合わせの試験が要り、基準画像（`/dashboard` を写すもの全部と command-palette）を作り直す。

### 2.2 選択肢と推奨

| 案 | 中身 | 利点 | 欠点 |
| --- | --- | --- | --- |
| a | 何もしない（#882 を閉じる） | 費用が無い | W3 の宿題（在庫少のリンク先が期間で絞られない）が残る。チャートがキーボードで読めないまま |
| **b** | **ドリルダウンだけ**（第 1 段。§8 の D1〜D3） | 見本と宿題がある。部品が下流でも使える。基準画像が変わらない。`@banto/charts` は足すだけ（minor） | クロスフィルタは無い |
| c | ドリルダウン + クロスフィルタ（第 2 段の C1・C2 まで） | Issue の「やること」を全部満たす | 下流の利用が無い機能に、状態・見た目・試験の面積を足す。基準画像の作り直し |

**推奨は b**。クロスフィルタ（第 2 段）は**保留**にし、下流か派生アプリから要望が出たら着手する。この文書は、
第 2 段を後から足しても第 1 段の公開の口を壊さない形にしておく（§6.3、§7.4）。

最小の範囲（第 1 段）:

1. 一覧の定義のビューが引数を取れる（`?view=<id>&<引数>=<値>`。`lib/resource/`）。
2. `BarChart`・`PieChart` の印を、マウスとキーボードで選べる（`@banto/charts`。足すだけ）。
3. 見本: 価格帯のドーナツとカテゴリ別の在庫の棒から `/items` へ。KPI の「在庫少」のリンクに期間を持たせる。

## 3. 決めること 1 — template-scope §4.2 の内側に収まるか

線引き（2026-11-23、#716）: 利用者が編集できるのは**配置**だけ。**種類と中身**は作者がコードで登録する。
利用者がデータの出どころ・式・見た目を画面で組む口は作らない。

| 案 | 中身 | §4.2 との関係 |
| --- | --- | --- |
| **a** | 次元・どのウィジェットがどの次元を出すか・移る先の一覧と条件は、**作者がコードで登録する**。利用者がするのは「作者が見せた値を 1 つ選ぶ」ことだけ | **内側**。期間の選択（W3 の `SegmentedControl`）や、一覧の列フィルタと同じ種類の操作 |
| b | ダッシュボードに「条件を足す」帯を置き、利用者が項目・演算子・値を選ぶ | **外側**（データの出どころを画面で組む口）。採らない |
| c | 利用者が、ウィジェットごとに「どの次元に反応するか」を画面で切り替える | **外側**（中身の編集）。採らない |

**推奨は a**。内側に収めるための歯止めを、設計の制約として置く:

- 次元は閉じた集合（型で列挙する）。画面から足せない。
- 選べる値は、ウィジェットが描いている印の値だけ。値を打ち込む口は作らない。
- 1 つの次元に選べる値は 1 つ（同じ印をもう一度選ぶと解除）。AND / OR を組む口は作らない。
- 選択は保存しない（§6）。「絞り込みの組を名前を付けて残す」口は作らない。
- 移る先の一覧と条件は、作者が書いた関数が決める（§7.2）。URL に任意の項目・演算子を書ける文法は作らない（§7.1 の案 c）。

template-scope への追記: **第 1 段（ドリルダウンだけ）では要らない**（印からのリンクは、KPI のタイルのリンクと同じ）。
第 2 段に着手するときに、§4.2 の同じ行へ次の 1 文を足す（文面の案）:
「ウィジェットの印を選んでほかのウィジェットを絞る操作（クロスフィルタ）は、次元と反応するウィジェットを作者が
コードで登録する。利用者が条件を画面で組む口は作らない」。

## 4. 決めること 2 — 選択のイベントをどこで持つか

### 4.1 いまの形

- `@banto/charts` に、印を選ぶ口は**無い**。印（`BarChart` の `<path class="bar">`、`PieChart` の `<path class="slice">`）は
  `onpointerenter` / `onpointerleave` でツールチップを出すだけで、クリック・フォーカス・キーボードの操作は無い
  （`LineChart.svelte` の注記: ツールチップは補助なので、ポインターだけでよい）。
- 入れ物（`internal/ChartContainer.svelte`）は `role="img"` + `aria-label`。スクリーンリーダー向けの表の代わりは未実装（spec の規則 8 の後回し）。
- 例外は `LineChart` の「ズームを戻す」ボタンだけ。

### 4.2 選択肢

| 案 | 中身 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A** | **`@banto/charts` に足す**。`onMarkActivate` を渡したときだけ、印がフォーカスでき、クリック / Enter / Space で呼ばれる | 印そのものを選べる。キーボードとスクリーンリーダーの扱いを 1 か所で正しく作れる。下流のチャートでも使える | パッケージの公開の口が増える（足すだけ。minor）。`role="img"` の中に操作できる子は置けないので、入れ物の role を切り替える |
| B | テンプレートのウィジェットが、チャートの横に値の一覧（ボタンの並び）を自前で描く | charts を変えない。ボタンなので a11y は素直 | 印をクリックしても何も起きない。凡例と中身が重なる。ウィジェットごとに同じ部品を書く |
| C | テンプレートが、チャートの DOM（`.bar`）を探してクリックを拾う | charts を変えない | パッケージの中の DOM に依存する（壊れても型で気付けない）。キーボードの操作を作れない。**採らない** |

**推奨は A**。対象はまず `BarChart`（横・積み上げを含む）と `PieChart`（ドーナツを含む）の 2 つ。ほかの種類
（`ParetoChart`・`Histogram`・`ScatterChart`・`Heatmap` など）は、要望が出たら同じ形で足す。

### 4.3 公開 API の案（`@banto/charts`）

```ts
/** 選ばれた印。`TRow` はチャートへ渡した行の型。 */
export interface ChartMark<TRow> {
	/** 印の元になった行（`data` の要素）。 */
	row: TRow;
	/** `data` の中の位置。 */
	index: number;
	/** `category` の accessor が返した値。 */
	category: string;
	/** 系列の id（`BarChart` の `series[].id`）。`PieChart` には無い。 */
	seriesId?: string;
	/** 印の値（`formatValue` を通す前）。 */
	value: number;
}

// BarChart / PieChart の Props に足す（どれも省略可）
interface MarkProps<TRow> {
	/** 渡すと、印を選べるようになる（クリック・Enter・Space）。渡さなければ、今と同じ（操作なし・`role="img"`）。 */
	onMarkActivate?: (mark: ChartMark<TRow>) => void;
	/** 印の読み上げの名前。既定は「<category>: <formatValue(value)>」（積み上げは系列の名前も）。 */
	markLabel?: (mark: ChartMark<TRow>) => string;
}
```

- **`onMarkActivate` が無いとき、DOM も見た目も今と同じ**（基準画像が変わらないこと・既存の利用が壊れないことの根拠）。
- `onMarkActivate` があるとき:
  - 入れ物の role を `img` から `group` へ（`aria-label` はそのまま）。印は `role="button"` + `aria-label`（`markLabel`）。
  - **Tab で止まるのはチャート 1 つにつき 1 か所**（roving tabindex）。矢印キーで隣の印へ、Home / End で端へ、Enter / Space で選ぶ。
    フォーカスが入った印には、ポインターを載せたときと同じツールチップを出す。
  - フォーカスの輪は `--banto-*` のトークン（conventions §9。生値を書かない）。カーソルは pointer。
  - 細い棒・小さい扇でも押せるように、当たり判定は印の形より広く取る（棒は帯の幅いっぱい）。touch 密度で確かめる。
  - 矢印キーの移動先を決める関数は `core/` に純関数で置く（単体テストできる形。svelte に依存しない）。
- 読み上げの既定の文は `messages.ts`（i18n の第 1 層、conventions §13）に足す。アプリは `markLabel` で「〜を一覧で開く」まで言える。
- 第 2 段で足す見込み（第 1 段では足さない）: `markSelected?: (mark) => boolean`（`aria-pressed` と、選ばれていない印を薄くする見た目）。
- 採らなかった形: `markHref`（印を SVG の `<a>` にする）。リンクとしては素直だが、第 2 段（選択）で別の口が要り、口が 2 つになる。

### 4.4 charts を外すプリセットで壊れないこと

- **`onMarkActivate` を呼ぶのは、チャートのウィジェットの部品（`components/dashboard/charts/*.svelte`）だけ**。
  `removeCharts` はこのディレクトリと登録の `[scaffold:charts]` の領域を消すので、一緒に消える。
- 移る先を作る関数（§7.2 の `dashboardDrill.ts`）と、枠・ページの配線は **`@banto/charts` を import しない**。
  charts を外した後も、KPI の「在庫少」のリンク（期間つき）はそのまま動く。
- 第 2 段: 選択を出すウィジェットが 1 つも無くなるので、条件は空のまま。選択の帯は条件が空なら出さない。
  一覧のウィジェット（`lowStock`。`@banto/grid-svelte` はコア）は、絞られていない行を描くだけで壊れない。
- 確かめ方: 各 PR で `pnpm scaffold --preset <名前> --dry-run` を 4 プリセットと、charts だけ・dock だけを外す組み合わせで回し、
  外した後に `@banto/charts` の参照が残らないこと（§4.13.6 と同じ。フロントだけの変更では template-acceptance が走らないことがある）。

## 5. 決めること 3 — 切り離した窓（Tauri の pop-out）へ届けるか

いまの形: 切り離した窓は別の文書（`routes/panel/[id]/+page.svelte`）で、`createDashboardData()` を引数なしで呼ぶ。
期間は**届けていない**（§4.13.7 の b、§4.13.10）。窓を開く口（`popout.ts` の `panel_open`）が渡すのは id と title だけで、
戻りの知らせは「窓が閉じた」（`banto://panel-closed`）だけ。

| 案 | 中身 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **a** | **届けない**。切り離した窓は全件を描き、印は選べない（`onDrill` を渡さない → `onMarkActivate` が無い → 操作なし） | 期間と同じ規則で、説明が 1 つで済む。Rust（`src-tauri`）を触らない | 切り離した窓では、絞り込みもドリルダウンも使えない |
| b | 開くときの条件を URL のクエリで渡す | 開いた時点の絵は合う | その後は追随しない（古い条件のまま残る）。`panel_open` の変更が要る（このサンドボックスではコンパイルできない） |
| c | Tauri のイベントで、条件の変更を全部の窓へ配る | いつも合う | 窓の間の状態の同期（順序・開いた直後の初期値・閉じた後）を新しく作る。ブラウザーのタブで開いた `/panel/[id]` には届かない。期間も同じ扱いに直すことになる |

**推奨は a（届けない）**。明記すること:

- 切り離した窓のウィジェットは、**期間も選択も受け取らず、全件を描く**。
- 切り離した窓では、**印を選べない・ドリルダウンもしない**。この窓はシェルの無い窓で、中で `/items` へ移ると
  シェルつきの画面が小さな窓に出てしまう。主の窓を前へ出して移す口も作らない。
- 第 2 段: 選択を出しているウィジェットを切り離す / 非表示にしても、選択は消さない。選択の帯（§6.3）が
  ページの見出しに残るので、何で絞っているかと解除の口は見え続ける。

届ける要望が出たら、期間と一緒に c を別 Issue で設計する（期間だけ届かない形にしない）。

## 6. 決めること 4 — 絞り込みの状態を保存するか

### 6.1 選択肢

| 案 | 中身 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **a** | **保存しない**。ページの `$state` だけ（再読み込み・ページの出入りで空へ戻る） | 期間（W3）と同じ。配置の保存値（`dashboard.widgets`）に混ざらない。古い条件が残って「数字が少ない」と誤解されない | ドリルダウンして「戻る」と、選択が消えている |
| b | `/dashboard` の URL のクエリに載せる（`?category=…`） | 再読み込み・「戻る」で残る。URL で共有できる | 期間は URL に無いので、期間も載せ直すことになる。一覧の `?view=` と監査ログのクエリは「1 回きりの指示で、適用したら URL から消す」形で、URL を状態の写しにする先例が無い。印の値（データに由来する文字列）が履歴に残る |
| c | 利用者ごとに保存する（`createSavedSetting`） | 次に開いても同じ | 古い条件が黙って効き続ける。値がデータから消えたときの扱いが要る。grant セッション（閲覧公開）は設定を共有するので、ほかの画面の表示まで変わる |
| d | SvelteKit の `snapshot`（履歴の移動のときだけ戻す） | 「戻る」で残り、再読み込みや別の入り口では空 | 期間も同じ扱いにするのが自然で、範囲が広がる。**未検証**（adapter-static と Tauri の WebView での挙動を確かめていない） |

**推奨は a（保存しない・ダッシュボードの URL にも載せない）**。期間と同じ規則にそろえる。
「戻る」で消えるのが実際に困ると分かったら、期間と一緒に d を検討する（第 2 段の中の判断。第 1 段には選択が無いので関係しない）。

### 6.2 ドリルダウンの URL は別（保存ではなく、1 回きりの指示）

移る先の一覧の URL には条件を載せる（§7.1）。これは今の `?view=` と同じ扱いで、一覧は適用した後に
`replaceState` でクエリを消す（再読み込みで、利用者がその後に変えた条件を上書きしないため）。
載せる値は、作者が次元として見せた値（カテゴリの名前・価格帯の id・日付）だけで、秘密や個人の情報は載せない。

### 6.3 第 2 段の選択の帯（見込み）

選択があるときだけ、ページの見出しの下に帯を出す: 次元ごとのチップ（「カテゴリ: 〇〇 ✕」）と「すべて解除」。
チップと解除は `@banto/ui` の既存の部品で作る。文言はキー経由（ja・en）。キオスクでも出す（期間の操作と同じ理由: 配置の編集ではなく、保存もしない）。

## 7. データの流れと公開 API の案

### 7.1 ドリルダウン → 一覧の URL（`lib/resource/`）

いまの形: `ResourceListPage.svelte` は `?view=<id>` を読み、定義のビュー（`def.list.views`。`ResourceListView` は
`id`・`label`・`sort`・`filters`・`search`）か利用者の保存したビューを当て、クエリを消す。ビューは**固定**で、値を受け取れない。

| 案 | 中身 | 利点 | 欠点 |
| --- | --- | --- | --- |
| a | 固定のビューだけで済ませる（値ごとにビューを 1 つ書く） | `lib/resource/` を変えない | 価格帯（4 つ）は書けるが、カテゴリ（データで決まる）は書けない。期間（基準の日はデータで決まる）も渡せない |
| **b** | **定義のビューが引数を取れる**。`?view=<id>&<引数>=<値>`。引数の名前はビューが宣言し、値から条件を作る関数は作者が書く | 条件の形は作者のコードが決める（§3 の歯止め）。URL の文法が小さい。どのリソースでも使える | `lib/resource/`（コア）に手が入る |
| c | 汎用のクエリ（`?filter=<項目>:<演算子>:<値>`） | ビューを書かなくてよい | URL が「条件を組む言語」になる（§3 の線引きに近づく）。項目・演算子・値の検査を新しく持つ。**採らない** |

**推奨は b**。型の案（`apps/admin-template/src/lib/resource/types.ts`）:

```ts
export interface ResourceListView {
	id: string;
	label: () => string;
	sort?: SortState[];
	/** 固定の条件（今のまま）。 */
	filters?: FilterState[];
	search?: string;
	/**
	 * このビューが URL から受け取る引数の名前（`?view=<id>&<名前>=<値>`）。宣言した名前だけを読み、
	 * 適用した後に `view` と一緒に URL から消す。
	 */
	args?: readonly string[];
	/**
	 * 引数から条件を作る（`filters` に足す）。`null` を返すと、引数が正しくないとして
	 * ビューを当てずに知らせを出す。引数が 1 つも無い URL（メニューから選んだとき）では呼ばない。
	 */
	filtersFor?: (args: Readonly<Record<string, string>>) => FilterState[] | null;
}
```

- **引数つきのビューは、「ビュー」メニューには引数なしの形（`filters` だけ）で出す**。`filtersFor` だけのビュー
  （引数が無いと意味を成さないもの）をメニューから隠す印（`hidden?: boolean`）が要るかは、D1 で決める。
- **値は信用しない**（URL は外から来る）。読むのは宣言した名前だけ、長さの上限と制御文字の除外は監査ログのクエリ
  （`auditLogQuery.ts` の `cleanValue`）と同じ規則を `lib/resource/` に置く。値は条件の**値**にしかならず、項目と演算子は
  作者のコードが決める。サーバーの列は今までどおり ColumnMap の許可リストを通る（conventions §6）。
- **コア → オプションの逆依存は起きない**（conventions §4）。`lib/resource/` はダッシュボードも `@banto/charts` も知らない。
- 読み込みの方式との関係: 一覧は `viewForFields` で、その格子に無い項目の条件を**落とす**。items の「カテゴリ」は
  クライアントの格子だけにある派生の列（`toRow`）なので、サーバーの方式では条件が落ちて件数が合わない。
  見本は、**実在の列で書ける条件**（価格帯 = `price` の範囲、在庫少 = `stock`、期間 = `updatedAt`）を先に入れる。
  カテゴリは §10 の判断待ち。

### 7.2 ページの状態 → ウィジェット → 一覧（第 1 段）

```
+page.svelte ── filter（$state。期間）
   │  onDrill = (drill) => goto(drillHref(drill, filter, anchorDay))
   ▼
DashboardWidgetFrame ── data（今のまま）と onDrill を渡す
   ▼
charts/PriceBucketsWidget ── <PieChart onMarkActivate={onDrill && ((mark) => onDrill({ kind: 'priceBucket', … }))} />
   ▼（クリック / Enter / Space）
/items?view=price-band&band=100-149&since=2026-06-02 ── ResourceListPage が当てて、クエリを消す
```

型の案（`apps/admin-template/src/lib/banto/`）:

```ts
// dashboardDrill.ts（新規。@banto/charts を import しない）
export type DashboardDrill =
	| { kind: 'lowStock' }
	| { kind: 'priceBucket'; bucket: PriceBucketId }
	| { kind: 'category'; category: string };

/**
 * 移る先の URL。期間が「全期間」でなければ、期間の始まりの日（`periodStart` と `latestDay` で決めた
 * 具体的な日）を `since` で持たせる。一覧の側で基準の日を数え直さない。
 */
export function drillHref(drill: DashboardDrill, filter: DashboardFilter, anchorDay: string | null): string;

// dashboardWidgets.ts（足す）
export interface DashboardWidgetProps {
	data: DashboardData;
	height: number;
	/** 印から一覧へ移る。切り離した窓では渡されない（そのとき、ウィジェットは印を選べる形にしない）。 */
	onDrill?: (drill: DashboardDrill) => void;
}
```

- **ウィジェットは期間を知らないまま**（W3 の原則）。ウィジェットは「何を選んだか」だけを言い、期間を足して URL を作るのはページ。
- KPI の「在庫少」のリンク（`dashboardKpis.ts` の `link.href`）も `drillHref({ kind: 'lowStock' }, …)` で作る。
  W3 の「残したこと」（タイルの件数は期間で絞るのに、一覧は絞らない）がここで解ける。
- 件数が合う範囲: ダッシュボードは最大 `DASHBOARD_ROW_LIMIT`（20,000）行を読んで集計する。それを超えるデータでは、
  印の値と一覧の件数が合わないことがある（今の「在庫少」と同じ）。recipe に書く。
- `DASHBOARD_WIDGETS` の登録の型には欄を足さない（移る先はウィジェットの部品が決める。部品はチャートと一緒に消える）。

### 7.3 選択 → 状態 → ウィジェット（第 2 段。保留。見込み）

```ts
// dashboardPeriod.ts の DashboardFilter に足す（W3 が用意した道）
export type DashboardDimension = 'category' | 'priceBucket';
export interface DashboardFilter {
	period: DashboardPeriod;
	/** 次元ごとに選んだ値（1 つ）。無い次元は絞らない。 */
	selection: Partial<Record<DashboardDimension, string>>;
}

// 登録（DashboardWidgetDef）に足す
interface DashboardWidgetDef {
	/** このウィジェットの印が出す次元。 */
	selects?: DashboardDimension;
	/** 選択で絞った行を描く（`usesPeriod` と同じ考え方）。 */
	usesSelection?: boolean;
}
```

- **自分の出す次元では、自分を絞らない**（カテゴリの棒を選んでも、カテゴリの棒は全部残り、選んだ棒が目立つ）。
  ウィジェットへ渡す行は「期間 + 自分の次元を除いた選択」で絞ったもの。`createDashboardData` は、次元ごとに
  「その次元を除いた行」を遅延で 1 つずつ持つ（次元が 2 つなら最大 3 通り。`stats` は KPI の帯の分だけ計算する）。
  渡し分けは今と同じく枠の 1 か所（`dashboardDataFor`）。
- ウィジェットの props に、自分の次元の今の値と切り替えの関数を足す（`selects` のあるウィジェットにだけ渡す）。

### 7.4 第 2 段を入れるときに変わること（先に知っておく点）

第 1 段では「印を選ぶ = 一覧へ移る」。第 2 段では、同じ操作を「印を選ぶ = 絞る（もう一度で解除）」にし、
一覧へ移る口は選択の帯のリンク（「一覧で見る」）へ移すのが素直。**同じ操作の意味が変わる**ので、第 2 段の PR では
CHANGELOG の「消費側への注意」と recipe に書く。`@banto/charts` の口（`onMarkActivate`）は変わらない
（意味を決めるのはアプリの層）。§10 の判断 5。

## 9. 試験の方針

- **単体**（node で走る。runes は反応しない形でコンパイルされるので、effect に頼らず純関数で確かめる。§4.13.10 と同じ）:
  ビューの引数の読み取りと検査、`drillHref`、矢印キーの移動、既定の読み上げの文、（第 2 段）次元を除いた絞り込み。
- **e2e**: smoke に足す（charts と dock が要る場面は、ページの DOM ではなく**アプリの依存**で飛ばすかを決める。§4.13.9）。
  ハイドレーション前の操作の揺らぎは `toPass` で再試行する（#810）。キーボードだけの操作を必ず 1 本入れる。a11y の spec（axe）に
  印を選べるチャートのある画面を入れる。
- **visual**: 第 1 段は**基準画像を増やさず、変わらないことを完了条件にする**（静止の見た目は同じ。フォーカスの輪は e2e で
  属性とスタイルを見る）。第 2 段は選択の帯で見出しが変わるので、`/dashboard` を写すもの全部と command-palette を作り直す
  （Linux だけ。`visual-baselines.yml` を dispatch）。
- **scaffold**: PR ごとに 4 プリセットと、charts だけ・dock だけを外す組み合わせの `--dry-run` を自分で回す。
- **Tauri**: `src-tauri` は触らない（§5 の推奨 a）。切り離した窓は、ブラウザーのタブで開いた `/panel/[id]` で確かめる。
