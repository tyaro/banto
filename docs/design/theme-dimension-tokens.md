## 1. 経緯

PR #463（ファイアウォールの許可に必要な情報の表示、#219 段階 1 PR-A）のレビューで Codex が「AGENTS.md の
不変条件 6（UI は `--banto-*` トークンのみ）により、UI の寸法は theme のトークンを使う」と指摘した。ところが
`banto.css` には汎用の余白・文字サイズ・枠線幅のトークンが無く、指摘に従うにはトークンを新設するしかない。
#463 で一度 `--banto-space-1..4`・`--banto-font-size-xs/sm/md`・`--banto-border-width`・
`--banto-label-column-width` を足したが、**公開 API を増やす設計判断を機能の PR に混ぜない**というオーナーの
判断で外した。本書はその設計判断を独立に扱う。

## 2. 規約の正確な現状

### 2.1 本文

- **AGENTS.md 不変条件 6**: 「UI は `--banto-*` トークンのみ（生値は theme に集約）」。色と寸法の区別は無い。
- **conventions §9**（見出し「テーマトークンのみ・生値は theme に集約 [機械検査済み: packages の色値のみ]」）:
  「UI CSS は `var(--banto-*)` トークンのみを使い、色・寸法の**生値をコンポーネントに書かない**」。
  **寸法は明示的に対象に含まれている**。app 層（`apps/admin-template/src`）の生値は「正当化コメント付きの
  意図的例外としてのみ許容」。
- **機械検査**: verify-architecture の rule 5 `raw-colors` は `packages/` の `.svelte` の `<style>` だけを走査し、
  `#hex`・`rgb(a)(`・`hsl(a)(` だけを見る。**寸法は一切検査しない**。app 層も検査しない。
- **visual-refresh-plan.md §3.4**: Tailwind の `@theme` 橋渡しの目的として「トークンは banto.css、
  **余白は Tailwind**、影は各ページ、という三重管理を防ぐ。単一の情報源は常に `--banto-*` トークン」。
  §3.5 は compact 密度で「**余白トークンを 1 段階縮小**」と書くが、その余白トークンは作られておらず、
  実装（visual-refresh-design.md §4.1）はコントロール高とグリッド行高だけを切り替える。
- **付録 A.5（タイポグラフィ）**: 役割ごとのサイズ（display 24–28px / heading 16px / body 14px /
  caption 12px）を決めているが、**トークンとしては定義していない**（`--banto-font-size` は root の 14px だけ）。

### 2.2 実態との食い違い

規約の文言は寸法のトークン化を**必須**としているが、

1. 余白・文字サイズ・枠線幅に使えるトークンが存在しないので、文言どおりには書けない（§3 のとおり、
   既存コードの大半が生の rem / px）。
2. 機械検査は色だけなので、寸法の生値は CI で止まらない。見出しの注記「packages の色値のみ」は、検査の
   範囲の説明であって、寸法を規約から外す宣言ではない。
3. app 層の「理由コメント無しの生値は書かない」は、実際には色についてだけ守られている（寸法の生値に
   理由コメントは付いていない）。

つまり**文言は寸法まで求め、実装と運用は色（と半径・影・z・モーション・コントロール高）までで止まっている**。
ドリフトである。

### 2.3 Codex の指摘の位置づけ

- 文言に照らせば**指摘は正しい**（§9 は寸法を明記している）。
- ただし、従うための部品（トークン）が無く、周りのコード（同じ設定画面の `settings.css` を含む）も生値で
  書かれているので、**#463 単体で満たすことは設計判断なしにはできない**。#463 は周囲の書き方に合わせ、
  本書の決定を待つのが妥当（オーナーの判断どおり）。
- 本書が決めるのは「文言に実装を寄せる（A）」か「実装に文言を寄せる（B）」か、その中間（C）か。

## 4. 選択肢

### A. 余白・文字サイズ・枠線幅の段階トークンを theme に足す（文言に実装を寄せる）

新しいコードはトークンを使い、既存は範囲ごとに段階的に移す。

- 利点: §9 と不変条件 6 の文言どおりになり、レビューで今回のような指摘が出ても答えがある。付録 A.5 の
  役割がトークンとして実体を持つ。§3.5 の「余白トークンを 1 段階縮小」を将来実装する足場になる。
  散らばった小さい文字サイズ（5 種）を 2〜3 段に整理できる。
- 欠点: 公開 API が増える（後から値や名前を変えにくい）。移行は約 620 宣言（余白 354・文字 167・枠線 102）。
  刻みから外れた値の丸めで画面が 1〜1.5px 動き、**visual のベースライン画像の再生成**（Linux 生成。
  visual-baselines.yml の dispatch）が範囲ごとに要る。
- 密度: 名前を値に結び付けなければ（§5.1）、compact で余白を縮める余地が残る。
- 派生アプリ: 足すだけなので壊れない。派生側が写したコンポーネントは生値のまま動く。upgrading に「任意」と書く。

### B. 規約を「寸法は生の rem でよい」と明確にする（実装に文言を寄せる）

色・半径・影・z・モーション・部品の形（コントロール高など）だけをトークンにし、余白・文字サイズ・枠線幅は
生の rem を正とする。

- 利点: 移行ゼロ、公開 API も増えない。現状の運用をそのまま追認する。
- 欠点: §9 と不変条件 6 の文言を後退させる。付録 A.5 の役割は守る手段が無いまま（散らばりが続く）。
  §3.5 の「余白の 1 段階縮小」は実現できなくなる（諦めると明記が要る）。テーマ（Glass など）や派生アプリが
  余白・文字の大きさを一括で変える手段が無い。
- 密度: 余白は密度に追従しない（今と同じ）。

### C. 中間: 文字サイズと枠線幅だけトークン、余白は生値

- 利点: 文字サイズは役割（付録 A.5）がはっきりしていて、散らばりの整理に効く。枠線幅は値が 1 種類なので
  移行は機械的。余白は値が多く丸めの手間が大きいので後回しにできる。
- 欠点: 余白について文言との食い違いが残る（規約に「余白は例外」と書く必要がある）。§3.5 は実現しない。
- 密度: 余白を縮める話は残らない。

### 比較

| 観点 | A | B | C |
| --- | --- | --- | --- |
| 規約の文言との一致 | 一致 | 文言を後退させる | 余白だけ例外を明記 |
| 公開 API の追加 | 余白 8・文字 5・枠線 2 程度 | なし | 文字 5・枠線 2 程度 |
| 移行の量 | 約 620 宣言（範囲ごとに段階的） | 0 | 約 270 宣言 |
| 画面のずれ | 余白の丸めで 1〜1.5px（ベースライン再生成） | なし | 文字の丸めで 0.5px 前後 |
| 密度（compact で余白を縮める） | 可能（D3） | 不可 | 不可 |
| 派生アプリ | 後方互換（任意で採用） | 影響なし | 後方互換 |

### 推奨: A（ただし段階的に。足すのが先、移行は範囲ごと、機械検査は最後）

理由: 規約は寸法を明記しており、文言を後退させる理由（トークン化が技術的に不適切）は見当たらない。
食い違いの原因は「トークンが無い」ことで、足せば新しいコードから文言どおりに書ける。値の分布は余白が
0.25rem 刻みの 8 段に半分以上乗り、文字サイズは 5 段に収まるので、段階は無理なく決まる。移行は急がず、
各範囲の PR でベースラインを見ながら進める。

## 5. 推奨案の具体（A）

### 5.1 命名の規則

- `--banto-<種類>-<段>`。種類は `space` / `font-size` / `border-width`。
- 余白は**序数**（`-1`, `-2`, …）。値を名前に埋め込まない（`-4` が「4 × 0.25rem」を約束しない）。
  compact で値を縮めても名前が嘘にならない（D3）。結果として 1〜6 は 0.25rem の倍数と一致するが、
  それは約束にしない。
- 文字サイズは**大きさの呼び名**（`xs` / `sm` / `md` / `lg` / `xl`）。本文（body）は root の `1rem` で、
  継承に任せる（トークンを付けない）。`md` は「本文より一段小さい補足」で、本文ではない（D4）。
- 部品専用の形（列幅・アイコンの大きさ・ランチャーなど）は汎用の段階に入れない。2 つ以上の部品が同じ値を
  共有する場合だけ、既存の `--banto-shell-*` のように用途名で足す。

### 5.2 トークンと値（案）

	--banto-space-8: 3rem; /* 42px — 空状態など */

| 余白 | `0.65rem`・`0.7rem`・`0.8rem`・`0.85rem` | `space-3`（0.75rem） | ≤ 1.4px |
| 余白 | `0.9rem`・`1.1rem` | `space-4`（1rem） | ≤ 1.4px |

| 枠線 | `1px` / `2px` | `border-width` / `border-width-strong` | なし |

トークンにしないもの（例外。理由コメント不要の範囲として規約に書く案。D6）:

- `0`、`em` 単位の値（文脈相対。アイコンと文字の間隔など）、`1px` 未満の調整やヘアラインの
  オフセット（`-1px` の margin など）、`calc()` の中で部品の形から導く値。
- 部品の形（幅・高さ・列幅・アイコンの大きさ）。これは §9 の「寸法」に含めず、部品ごとのローカルな
  カスタムプロパティか、共有されるなら用途名のトークン（§5.1）にする。#463 の
  `--banto-label-column-width` はこれに当たる（D7）。
- `3px`・`4px` の縁（左端の強調バー等。8 件）は部品の形として扱い、段階に入れない。

### 5.3 密度（D3）

推奨は「**最初は余白を密度で切り替えない**」。compact の今の上書き（コントロール高・グリッド行高）は
変えない。序数の命名で将来の切り替え（compact で `space-3`〜`space-6` を 1 段階ずつ小さい値に）を
可能にしておき、移行が進んで余白トークンの利用が揃ってから別に決める。移行の途中で切り替えると、
移した部品だけが縮み、画面の中で余白がちぐはぐになるため。

### 5.4 Tailwind の橋渡し

`app.css` の `@theme inline` に余白（`--spacing`）や文字サイズを足すのは**しない**。admin-template は
ユーティリティを使っておらず（§3.4）、Tailwind v4 の `--spacing` は単一の基数で序数の段階と対応しない。
派生側が使いたくなったら、その時に `--text-*` / `--spacing` の対応を決める。

## 7. 判断が要る点（D1〜D9）

| 論点 | 推奨 |
| --- | --- |
| D1 方針 | **a: 段階トークンを足し、段階的に移す（§4 の A）** |
| D2 対象の種類 | **a: 余白・文字サイズ・枠線幅の 3 種** |
| D3 密度で余白を切り替えるか | **b: 最初は切り替えない（序数の命名で余地だけ残す）** |
| D4 文字サイズの段と名前 | **a: xs / sm / md / lg / xl の 5 段、本文は継承（トークン無し）** |
| D5 刻みから外れた既存値 | **a: 近い段に丸め、範囲ごとの PR でベースラインを再生成** |
| D6 規約の文言 | **a: §9 に「寸法 = 余白・文字サイズ・枠線幅の段階」と例外の一覧を書く（PR-1）** |
| D7 部品の形（列幅など） | **a: 汎用の段階に入れない。共有されるときだけ用途名で足す** |
| D8 機械検査 | **b: 移行が終わった範囲から font-size と border-width だけ検査に足す** |
| D9 charts の文字サイズと文字幅の見積もり | **b: 共通の段（rem）に移し、余白計算は描画した要素の実際の文字サイズを読んで見積もる** |

### D1. 方針

- **a（推奨）**: §4 の A。足すのを先に、移行は範囲ごと、検査は最後。
- b: §4 の B。規約を後退させ、寸法は生の rem を正とする。移行ゼロだが、付録 A.5 と §3.5 の意図を諦める。
- c: §4 の C。文字サイズと枠線幅だけ。余白の食い違いは例外として規約に残る。

### D2. 対象の種類

- **a（推奨）**: 余白・文字サイズ・枠線幅。
- b: 加えて行送り（line-height）と字の太さ（font-weight）。付録 A.5 には行送りとウェイトもあるが、
  生値の件数を本書では数えていない。必要なら a の後で別に調べる。

### D3. 密度で余白を切り替えるか

- a: PR-1 から compact で `space-3`〜`space-6` を 1 段階縮める（visual-refresh-plan §3.5 の当初の意図）。
  移行の途中では、移した部品だけが縮んでちぐはぐになる。
- **b（推奨）**: 最初は切り替えない。移行が揃ってから a を別に決める。
- c: 切り替えないと決め、§3.5 の「余白の 1 段階縮小」を設計書から消す。

### D4. 文字サイズの段と名前

- **a（推奨）**: `xs` 0.7rem / `sm` 0.8rem / `md` 0.875rem / `lg` 1.125rem / `xl` 1.75rem。本文は 1rem の継承。
  #463 で試した `xs/sm/md` と名前が揃う。`md` が本文より小さいのは分かりにくいので、banto.css の
  コメントで明記する。
- b: 役割名（`--banto-font-size-caption` / `-heading` / `-display` …）。付録 A.5 と直結して意味は明確だが、
  役割に当てはまらない使い方（バッジ・極小ラベル）の置き場が曖昧になる。
- c: 小さい側を 2 段に絞る（`0.8rem` と `0.875rem` を 1 つにまとめる）。段は減るが、最多の `0.8rem`（51）か
  `0.85`/`0.875rem`（32）のどちらかが一律に 0.7〜1px 動く。

### D5. 刻みから外れた既存値

- **a（推奨）**: §5.2 の表の規則で近い段に丸める。画面が 1〜2px 動くので、範囲ごとの PR でベースラインを
  再生成して目で確かめる。
- b: 中間の段（`0.4rem` など）を足して画面を動かさない。段が 12 前後に増え、段階の意味が薄れる。
- c: 刻みに乗る値だけ移し、外れた値は生値のまま残す（理由コメント付き）。画面は動かないが、98 件の
  例外が残る。

### D6. 規約の文言

- **a（推奨）**: PR-1 で §9 に「寸法とは余白・文字サイズ・枠線幅の段階のこと。部品の形（幅・高さ・列幅）と
  §5.2 の例外は含まない」と書き、見出しの注記の検査範囲を更新する。不変条件 6（AGENTS.md）は要約なので
  変えない。
- b: 文言は変えず、本書を参照するだけ。何が「寸法」かの解釈がレビューのたびに揺れる。

### D7. 部品の形（列幅など）

- **a（推奨）**: 汎用の段階に入れない。部品のローカルなカスタムプロパティか生値（理由が自明な形）で書く。
  2 つ以上の部品・アプリが共有するときだけ、用途名で theme に足す。#463 の `--banto-label-column-width` は
  今は消費者が 1 つなので足さない。
- b: ラベル列幅など、よく出る形を最初から theme に足す。公開 API が用途ごとに増えていく。

### D8. 機械検査

- a: 検査を足さない（レビューで守る）。
- **b（推奨）**: 移行が終わったパッケージから、`font-size` と `border-width` の生値だけを rule 5 と同じ方式
  （`packages/` の `<style>`、許可リスト付き）で検査する。余白は `em`・`calc()`・部品の形の例外が多く、
  誤検知が多いので検査しない。
- c: 余白も含めて全部検査する。例外の許可リストが大きくなる。

### D9. charts の文字サイズと文字幅の見積もり

charts は軸ラベルの幅を文字サイズから見積もって余白を決める（`core/labels.ts` は既定 11px、
`LineChart` などは文字サイズを渡していない）。CSS の文字サイズだけを rem のトークンに変えると、root の
文字サイズを変えた環境やトークンを上書きした派生アプリで、実際の文字（例: root 20px なら sm = 16px）と
見積もり（11px）がずれ、長いラベルが切れる。14px の標準環境でベースラインを作り直すだけでは見つからない。

- a: charts だけ px の専用トークン（例 `--banto-chart-font-size-sm: 11px`）にし、見積もりは同じ px の定数を
  使う。root の文字サイズに追従しない（いまと同じ）。共通の段とは別の系統が残る。
- **b（推奨）**: 共通の段（`--banto-font-size-xs/sm/md`）に移し、余白の計算は描画したラベル要素の
  計算済みの文字サイズ（`getComputedStyle(...).fontSize`）を読んで `labels.ts` に渡す。読めない環境（SSR・
  テスト）では今の 11px を既定値に使う。root の文字サイズやトークンの上書きに追従する。
- c: 見積もりをやめ、描画後に実測（`getBBox`）して余白を決め直す。正確だが、描画が 2 回になり変更が大きい。

PR-5 の検証条件（b のとき）: (1) root の文字サイズを 14px 以外（例 20px）にした状態、(2) `--banto-font-size-sm`
を上書きした状態の両方で、長い軸ラベルが切れず、余白が文字サイズに追従することを単体テストか visual で
確かめる。

## 8. 未確認の点

- 行送り（line-height）・字の太さ（font-weight）の生値の分布は数えていない（D2-b）。
- `width` / `height` / `min-width` などの部品の形の生値は数えていない（D7 で対象外とする前提）。
- 派生アプリ（temp-scada など）での余白・文字サイズの書き方は調べていない。足すだけなので影響は無い想定。
