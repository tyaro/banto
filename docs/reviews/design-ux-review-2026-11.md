## 1. 現状の見立て

- **強み**: 土台の作り込みが深い。二形態（Tauri / LAN）の対称、RBAC と監査、トークンの一元化、
  キーボード操作と forced-colors まで入った a11y、仮想スクロール＋セル編集＋範囲コピーのグリッド、
  v7 のピッカー群、768 幅で下タブバーに変わるドック。
- **弱み 1（最大）**: 同梱画面が、エンドユーザー向けの製品画面ではなく保守者向けの機能デモになっている。
  マイルストーン番号・パッケージ名・内部アーキテクチャの説明が画面の文言に出ており、アプリ作者は
  コピー後にまずそれを剥がすことになる。
- **弱み 2**: `@banto/ui` に Svelte 部品としての Button / Tabs / Tooltip / Combobox / 確認ダイアログが無い。
  ページ側が `banto-btn` クラス・`window.confirm`・手書き CSS で補っている（items 一覧は 1,191 行）。
  なお、タブ・スイッチ・下線型入力は theme の opt-in クラスとして共通化済み（ADR-0023 / 0026）。
- **弱み 3**: 「リソース定義」があるのに画面を生成しない。1 リソースの追加が 9 ステップのコピー作業のまま。
- **弱み 4**: 見た目は破綻が無いが、個性と階層が弱い。システムフォント、最小 9.8px の文字、
  Tailwind 既定そのままの青、緑が 2 つ並ぶチャート配色、絵文字アイコンの混在。

## 2. 提案一覧

規模は S / M / L。「制約」は既存の決まりごととの関係。

### A. ビジュアルデザイン

#### A-1. 文字スケールの底上げと数値用書体の整備（M）

- root が 14px で `xs = 0.7rem = 9.8px`、最も多く使う `sm = 11.2px`
  （`packages/theme/src/css/banto.css` の `--banto-font-size-*`）。日本語の業務画面で 10px 未満は、
  現場端末や高齢の利用者には厳しい。
- 最小を 12px とし、スケールを 12 / 13 / 14 / 16 / 20 / 28 に組み直す。
- 書体は system-ui 任せで、OS ごとに数字の幅と字面が変わる。数字・英字用の可変フォントを 1 本同梱し、
  グリッド・KPI・チャート軸の既定を `tabular-nums` にする。
- 効果: 可読性の底上げ。OS をまたいで見た目が揃い、visual ベースラインの揺らぎも減る。
- 制約: フォントの同梱は conventions §3（依存を足さない）の精神に触れる。npm 依存ではなく静的資産なら
  回避できる。ベースラインの全再生成が必要。

#### A-2. カラーシステムを役割ベースで再設計する（チャート配色を含む）（M）

- チャートの系列 2（`#1baf7a`）と系列 4（`#008300`）がどちらも緑で、ドーナツや積み上げで隣り合うと
  見分けにくい。`--banto-accent-gradient` は紫 `#7c3aed` を生の値で持つ。primary の青は
  Tailwind 既定の `#2563eb` のままで、Banto らしさが無い。
- ニュートラル 12 段＋ブランド 1 色＋状態 4 色を OKLCH で定義し、ライト / ダークを同じ式から導出する。
- チャートは色覚の違いで検証した 8 色のカテゴリ配色に加え、sequential / diverging の 2 系統を持つ
  （ヒートマップは今、青の濃淡だけ）。
- `--banto-brand-hue` 1 つを変えれば全体が追従するようにする。
- 効果: 作者が自社の色に 1 行で変えられる。チャートの読み違いが減る。
- 制約: トークン名は変えず値だけ変えられる。ブランド色相の変数は新規トークンの追加。

#### A-3. glass プリセットのヘッダーの読みやすさを直す（S）

- `dashboard-launcher-dark-glass-1440x900` で、スクロール中のチャートの文字がヘッダーのタイトルに
  透けて重なる。ドックのぼかしも `blur(1px)` と弱い。
- ヘッダーは blur 16px 以上＋不透明度 80% 以上にするか、スクロール時だけ不透明に切り替える。
- 制約: なし。

#### A-4. 奥行きと密度の階層づけ（M）

- 全カードが同じ白地＋1px 枠＋同じ余白で、dashboard は 14 枚のカードが同じ重さで並ぶ。
  KPI 行は影なし、主役のチャートは一段大きく、補助カードは枠だけ、という 3 段の surface 階層を決める。
- density 軸は寸法スケールにまだ連動していない（`banto.css` のコメント「Not switched by the density
  axis yet (D3)」）。コンパクトで行高・余白・文字が一括で締まるようにする。
- 制約: なし。

#### A-5. アイコンの統一（絵文字をやめる）（S）

- 分析ワークスペースのパネルとチップが 📈🥧📊📝 の絵文字
  （`apps/admin-template/src/routes/(app)/dashboard/+page.svelte`）。OS ごとに絵柄が変わり、
  他の線アイコンから浮く。
- 制約: なし。

### B. UX・操作フロー

#### B-1. 同梱画面から開発者向けの説明を剥がし、製品画面にする（M）

- エンドユーザーが見る位置に内部事情が出ている。
  - items 一覧の上の説明に「M3」「M5」「M6」「BantoGrid」「DataProvider」「REST/SSE経由」
    （`apps/admin-template/messages/ja.json` の `items.note`）。
  - 「クライアント / サーバー」のモード切替がツールバーの主役の位置にある。これは実装方式で、
    利用者の選択肢ではない。
  - dashboard の節見出しが「チャート拡張（v2）」「チャート拡張（M24）」、カードの説明に
    「（BarChart stacked）」、ワークスペースに「M8、@banto/dock-svelte」。
  - settings に「仕様 §12.1 / M12」「設定DB（M12）」。
- 2 層に分ける。機能デモは `/ui-demo` と同じデモ専用ルート（「グリッド実験室」「チャート見本」）へ移し、
  `/items` と `/dashboard` は「飲料卸の在庫管理」という 1 つの筋で通した、本物らしい画面にする。
  開発者向けの解説は、デモビルドでだけ出る注釈（画面隅の「?」から開くドロワー）にまとめる。
- 効果: ライブデモの第一印象が「部品の見本市」から「このまま使えそうなアプリ」に変わる。
  作者はコピー後に文言を剥がさなくてよい。
- 制約: なし。scaffold.mjs の remover が文字列一致で編集するので追従が要る。

#### B-2. 一覧のツールバーの整理と「クイック検索＋フィルタチップ」（M）

- items のツールバーは 7 つの操作（モード切替、グループ化、列、帳票、CSV エクスポート、
  CSV インポート、新規作成）が横一列。768 幅ではあふれる。
- 主操作は「新規作成」だけを残し、CSV 入出力・帳票・列・グループ化は「…」メニューと「表示」メニューへ。
  左には全列を横断するクイック検索を置く。
- フィルタは今、列ヘッダーの ▾ の中にしか無い。適用中の条件をグリッドの上にチップで並べ、× で外せる
  ようにする。
- 効果: 最も頻度の高い「探す」が 1 操作になり、何で絞っているかが常に見える。
- 制約: 全列検索はサービス層の `column_map()` ホワイトリスト経由なら conventions §5 を破らない。

#### B-3. 詳細はページ遷移ではなく右ドロワーを既定に（M）

- 行の先頭の「開く」リンク列から別ページへ遷移するため、戻ったときに一覧の位置とフィルタの復元が要る。
- 行クリックで右ドロワーに詳細フォーム＋添付＋その行の変更履歴を出し、↑↓ で前後の行へ移る。
  URL は `?id=` で共有でき、全画面表示はドロワーの拡大ボタンから。「開く」列は廃止する。
- 制約: なし（`OverlayPanel` / Drawer は既存）。

#### B-4. `window.confirm` をやめ、「取り消せる操作」を基本にする（S〜L）

- 削除・リストア・認証の無効化が OS のネイティブ confirm（items 詳細、users、settings の
  DataSection・SecuritySection、login の 6 か所）。テーマも i18n の書式も効かず、Tauri と各ブラウザで
  見た目が違う。
- 行の削除は即時実行＋トーストの「元に戻す」（ToastHost はアクション付きに対応済み）。
  ユーザー削除や DB リストアのような重い操作は、対象名の入力を求める `ConfirmDialog` 部品にする。
- 制約: ConfirmDialog だけなら S で制約なし。Undo は論理削除か遅延コミットが要り、
  conventions §1（mutating は両経路で同一監査）の中で delete / restore の 2 イベントを定義する必要がある。

#### B-5. コマンドパレットを「レコード検索＋操作」まで広げる（M）

- パレットの中身はナビゲーションとテーマ切替だけ（`apps/admin-template/src/lib/commands.ts`）。
- リソース定義から「商品を検索: …」「商品を新規作成」「ユーザーを追加」「最近開いたレコード」を
  自動登録する。ヘッダーの検索欄をそのまま全体検索にする。
- 制約: パレットはオプション資産なので、登録 API をコア側に置き、コア → オプションの逆依存を作らない
  （conventions §4）。

#### B-6. 空状態と初回の体験を設計する（M）

- デモでユーザー管理を開くと「この環境では利用できません」で行き止まりになり、管理機能の売りが見えない。
  デモ用の InMemory ユーザー・監査ログのプロバイダを足し、読み取りだけでも画面を見せる。
- 実環境の初回起動も、管理者作成のあとに「サンプルデータを入れる／空で始める／CSV を取り込む」の
  3 択と、LAN 共有の案内を出す。
- 制約: conventions §10（demo は明示拒否）を、デモ専用の読み取りモックを許す形に変える必要がある。

#### B-7. ログイン画面の左半分を情報に使う（S）

- 左パネルはロゴとキャッチコピーだけで、画面の半分が装飾。アプリ名・接続先（この PC / LAN 上の
  どの PC か）・バージョン・管理者からのお知らせ 1 行を出す。作者はロゴ・背景・コピーを設定 1 か所で
  差し替えられるようにする。
- 制約: お知らせ文は設定 DB に 1 項目追加。

### C. UI 部品

#### C-1. `@banto/ui` に基礎部品を揃える（L）

- 今あるのは PageHeader / SurfaceCard / StatusBadge / IconButton / Menu / 各ピッカー / CommandPalette /
  Toast / Empty・Error・Loading。Modal / Drawer は薄いラッパー。
- 無いもの: Button、Tabs、Tooltip、SegmentedControl、Combobox、ConfirmDialog、Pagination、
  Breadcrumb、表のスケルトン、Banner。ページ側は `class="banto-btn banto-btn--secondary"` を直書きし、
  items のモード切替などは各ページの手書き。
- Button は loading / icon / size / danger を props で持ち、「処理中は文言を差し替える」代わりに
  スピナー＋幅固定にする。タブ・スイッチは theme の共通クラス（ADR-0023 / 0026）を部品の中身に使う。
- 制約: template-scope の「段階 2 に Modal / Drawer を入れない」判断の見直しが要る。

#### C-2. フォームの型と配置を増やす（L）

- FieldType は 9 種（`packages/forms/src/types.ts`）、レイアウトは 1 列固定。
- 型: 参照選択（他リソースを検索して選ぶ combobox）、radio / segmented、複数選択、通貨・単位つき数値、
  ファイル。配置: セクション見出し、2〜3 列、条件つき表示（`visibleWhen`）、ヘルプ文。
- 制約: 参照選択は DataProvider に検索の契約を足すので、パッケージ契約（conventions §4 / §5）の拡張。

#### C-3. グリッドのセル表現と行選択（L）

- セルは `format` で文字列にするか、`cell` で `{ text, href }` を返すだけ
  （`packages/grid-svelte/src/types.ts`）。バッジ、進捗バー、行内スパークラインが出せない。
- `renderer: 'badge' | 'progress' | 'link' | 'boolean' | 'sparkline'` と snippet の差し込み口、
  チェックボックスによる行選択と一括操作バー、列の固定、行高の密度連動、条件つき書式（在庫が閾値未満なら色）。
- 制約: 一括操作は両経路＋監査の対で実装する（conventions §1）。グリッド core の純関数分離を崩さない。

#### C-4. 保存ビュー（名前つきの絞り込み・並び・列構成）（M）

- GridState は sort / filters / order / widths / hidden / groupBy を 1 つの値で持つ。保存の UI だけが無い。
- 「在庫僅少」「今月更新」のようなビューをタブで並べ、個人用／全員共有を設定 DB に保存する。
  KPI カード「在庫僅少」を押すと該当ビューに飛ぶ。
- 制約: 共有ビューは settings の保存経路を使えば制約内。

#### C-5. 監査ログを「読める」画面にする（M）

- 詳細は JSON を整形して出すだけ。変更前後のフィールド差分表、操作者・期間・リソースの絞り込み、
  「対象を開く」リンク、レコード側の「このレコードの履歴」タブ（B-3 のドロワーに載せる）にする。
- 制約: detail に before / after を構造化して入れるなら、conventions §5（監査 detail に秘密を入れない）の
  ためにフィールドのマスク指定が必須。

### D. 機能

#### D-1. ダッシュボードを利用者が編集できるウィジェット盤にする（L）

- dashboard は 927 行の固定ページで、下に別枠の「分析ワークスペース」（dock）がある二重構造。
- KPI・チャート・一覧・メモを同じウィジェット型にし、追加・並べ替え・サイズ変更・期間フィルタの共有を
  1 つの盤で行う。チャート間のクロスフィルタと、チャートから該当レコード一覧へのドリルダウンも入れる。
- 制約: template-scope §4.2（画面エディタ / コードレスビルダーは入れない）に近い。配置の編集だけで、
  ウィジェットの種類は作者が登録する、という線引きなら範囲内とも言える。要判断。

#### D-2. LAN 共有を「QR 1 枚」で終わらせる（M）

- 接続まわりは到達確認・ファイアウォール状態・変更ダイアログと厚い（settings 配下に約 10 ファイル）が、
  利用者のゴールは「隣の人のスマホや PC で開ける」こと。QR と到達確認は既に settings の接続カテゴリにある。
- 「共有する」ボタン 1 つで URL と QR → 到達チェックの結果（緑／赤）→ ダメなときの直し方 1 つ、の
  3 ステップにまとめ、詳細パネルは「詳しく」に畳む。ヘッダーに「LAN 共有中・接続 3 台」を常設する。
- 制約: 接続台数は SSE の接続数から出せる。

#### D-3. 現場端末向けの「タッチ」密度と大型表示（M）

- 密度は標準／コンパクトの 2 つで、操作高 36px は手袋やタッチパネルには小さい。
  3 つ目の密度「タッチ」（操作高 48px、行高 52px、文字 16px）を足し、キオスク表示では遠くから読める
  大型 KPI にする。
- 制約: A-4 の density 連動が前提。

#### D-4. 切断時のふるまいを見せる（M）

- LAN のブラウザ側はサーバー PC がスリープすれば切れる。今はページ単位の ErrorState だけ。
- 切断中はヘッダーに帯を出し、再接続を自動で試み、編集中の下書きは保持（forms の draft 機構）、
  復帰時に「他の人が変更しました」を差分で見せる。
- 制約: なし。

### E. アプリ作者の開発体験

#### E-1. リソース定義 1 つから画面を作る `ResourcePage`（L）

- `ResourceDefinition` は name / label / icon / schema / capabilities を持つ
  （`packages/admin-core/src/registry.svelte.ts`）のに、実際の画面は items の 3 ルート＋2 グリッド
  （約 1,850 行）をコピーして書き換える（[add-resource](../recipes/add-resource.md) のステップ 8）。
  ナビも `NavIconKey` / `NavLabelKey` の union を手で足す。
- `<ResourceListPage resource="orders" />` と `<ResourceDetail />` を用意し、列・フィルタ・CSV・保存ビュー・
  ドロワー編集・権限による出し分けを既定で持たせる。崩したい所だけ snippet で上書きする。
  ナビとコマンドパレットの項目は registry から導出する。
- 効果: フロント側の追加が「定義ファイル 1 つ＋ルート 1 行」になり、B-2 / B-3 / C-3 / C-4 の改善が
  全リソースに一度で届く。
- 制約: scaffold.mjs の文字列一致 remover と template-acceptance の作り直しが要る。

#### E-2. `pnpm banto add resource` のジェネレータ（Rust 側まで）（L）

- 9 ステップのうち 1〜6 は Rust 側（マイグレーション 2 方言、サービス、REST、Tauri コマンド、
  対称テスト、監査）の定型コピー。フィールド定義 1 つから両方言の SQL・サービス・両経路・denied テスト・
  フロント定義を出す。生成物は普通のコードとして残し、以後は手で直す。
- 制約: 破らない。むしろ conventions §1 を機械的に守らせる。Node スクリプトなら依存の追加も不要。

#### E-3. テーマを試せるページ（M）

- ブランド色相・角丸・密度・フォントをスライダーで変えて全部品・グリッド・チャートに即時反映し、
  結果を CSS として書き出すページをデモビルドに足す。A-2 のブランド色相の変数と組で効く。
- 制約: デモ専用ルートなのでなし。

## 3. 推しの順位（インパクト順）

1. **B-1 同梱画面の製品化** — 規模 M で第一印象が最も変わる。ライブデモと README の説得力に直結し、
   作者の初日の作業も減る。
2. **E-1 `ResourcePage`** — テンプレートの価値は「2 本目のリソースがどれだけ速く・きれいに立つか」。
   一覧と詳細の改善が全リソースへ届く乗り物になる。
