## コンテキスト

hyper 1.x は、応答を待っている間に相手の FIN を読むと接続を閉じ、service の future（= handler）を捨てる。
handler が `.await` をまたいで副作用を重ねていると、そこで途中のまま止まる。banto の書き込みの handler は
「確定 → セッションの失効 → 監査」の順に `.await` を重ねているので、クライアントが応答を待たずに切れると、
**アカウントは作られたのに監査が残らない**、ということが起きる。この PR の試験
（`apps/admin-template/core/src/rest/tests/detach.rs`）は、層を外すと「作成あり・監査なし」と「作成なし」の両方を
実際に再現した。

下流（banto-industrial の ChronoGazer）は handler ごとに `run_detached` で包んで避けていたが、包み忘れが残る。
banto 自身の handler は包んでいなかった。

## 決定

### 1. 層は `BoundServer::serve` の 1 か所

`BoundServer::serve` が、router 全体のいちばん外側に手書きの層（`detach::detach_writes`、
`axum::middleware::from_fn_with_state`）を 1 つ掛ける。**POST・PUT・PATCH・DELETE** の要求は、内側の全部
（CSRF の検査・認証・ロールのガード・handler・監査）を `tokio::spawn` した別のタスクで走らせ、接続の側は
その終わりを待つだけにする。接続が切れて待つ側が捨てられても、タスクは最後まで走る。GET・HEAD・SSE は今のまま。

- **除外の口は作らない。ログインも切り離す**（オーナー決定 8）。派生アプリは `serve` を通るだけで全書き込みに
  掛かり、包み忘れが起きない。
- 依存は足さない（conventions §3。`tower-http` は入れない）。
- `oneshot` など、ほかの方法で router を動かすときは層が掛からない（切れる接続が無い）。
- handler が自分で `tokio::spawn` して包んでいても（下流の `run_detached`）害は無い。入れ子になるだけで、
  下流はこの版から外せる。

**切り離しの対象は「要求を読めた後」**。本体を読んでいる途中で切れた要求は、本体の読みが失敗して handler が
自分で終わり、何も起きない。

### 2. 冪等にはしない

切断したクライアントは結果を知らない。もう一度送ると二重に効く操作（作成など）は、これまでどおり守る側
（version、一意制約）の責任にする。層は操作 ID も再送の検出も持たない。

### 3. panic は 500

切り離したタスクが panic したら（`JoinError`）、接続を黙って落とさずに **500** を返す。本体は既存の
エラーの形のまま `{"kind":"other","message":"処理の途中でエラーが起きました。状態を読み直してから、もう一度試してください。"}`。
どこまで進んだかは分からないので、文言は「読み直してから」にする。`eprintln!` に `METHOD path` と理由を残す
（`tracing` は入れない、ADR-0004）。新しい `kind` は足さない: 画面は 500 の `other` を既に扱えていて、
kind を足すと `BantoError` と TS の写しの両方に手が入る。

### 4. 停止: 受付を止め、数えて、上限つきで待ち、残れば成功にしない

切り離した仕事は、サーバーのタスクを中断しても走り続ける。なので停止の順序を決める。

1. **新規の受付を止める**。`stop()` は最初に層の門を閉じる。以後に届いた書き込み（開いたままの接続に後から
   来たものも含む）は spawn せずに **503**（`kind: other`、「サーバーを停止しているため…」）で断り、状態を
   変えない。門の判定と数え上げはロックの下の 1 手なので、「断る」か「停止が数に入れて待つ」のどちらかになる。
   listener は今までどおり graceful shutdown で閉じる。
2. 走っている書き込みの数が 0 になるまで待つ。上限は **10 秒**（`DETACHED_WRITES_STOP_TIMEOUT`）。接続を
   待つ 5 秒（`STOP_TIMEOUT`、Issue #283）と**並行**に数えるので、停止は長くて 10 秒。
3. **上限を超えたら成功にしない**。`stop()` は `StopOutcome` を返す。`Finished` か、
   `WritesRemaining(RemainingWrites)`（今の数、`METHOD path` の一覧 — query は含めず、長さと件数に上限 —、
   終わりを待つ口）。残った書き込みは中断しない（中断すれば、防ぎたかった「途中で止まる」を自分で起こす）。
   `eprintln!` にも残す。
4. 上限を変えたい呼び手のために `stop_waiting_writes_for(limit)` を置く。

`stop()` の戻り値は `()` から `StopOutcome` に変わる（破壊的変更。`server.stop().await;` はそのまま通る）。
`#[must_use]` は付けない: 試験や終了の経路のように、結果を見なくてよい呼び手が多い。別の listener を
続けて起動する呼び手は、結果を見なければならない（doc に書く）。

### 5. 再設定は露出の向きで分ける（計画書 §10 の 17）

Tauri の `server_apply` は「旧い listener を止める → 新しい構成で起動する」。書き込みが残ったまま新しい構成で
起動すると、旧い世代の書き込みが新しい構成の後に状態を書き換えうる。残っているときは、**求められた構成の
listener を起動しない**。そのうえで、向きで分ける。

| 変更                      | 例                                            | 扱い                                                                                                                                                                                                                                                                                                                  |
| ------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 広げる・同等              | ポートの変更、bind を広げる、閲覧公開を始める | **切り替えの失敗**。保存も起動もせず、前の listener を戻す（既にある巻き戻し）。残った書き込みは、受け付けたのと同じ構成の下で終わる。`applyFailure` は `writesRemaining` / `restored`                                                                                                                                |
| サーバーの無効化          | 有効 → 無効                                   | 保存し、listener は閉じたまま。**成功**で返す（求められた状態になっている）。監査の行に残った書き込みを載せる                                                                                                                                                                                                         |
| 狭める（listener は要る） | 閲覧公開の停止、bind を狭める                 | 前の listener は**戻さない**（戻すと、止めたはずの口が開いたまま残る）。**保存し**、listener は閉じたまま、結果はエラー「保存して止めたが、書き込みが残っている。もう一度適用を」で返す。`applyFailure` は `writesRemaining` / `leftClosed`。監査は `ok`（保存された）で、`listening: false` と残った書き込みを載せる |

- 向きの判定は純関数 `banto_server::restoring_previous_stays_within(previous, requested)`:
  「前の構成へ戻しても、求められた構成より露出が広がらない」ときだけ真。比べるのは **listener の有無・bind・
  閲覧公開**の 3 つ（`ServerSettings` の項目は `enabled`・`bind`・`port`・`viewer_public` の 4 つで、ポートは
  露出を変えない）。bind は「ループバック ⊂ 個別のアドレス ⊂ その系統の全アドレス」で比べ、比べられないもの
  （ホスト名、別々のアドレス、`0.0.0.0` と `::`）は狭める側に倒す。**広げると狭めるが混ざった変更は狭める側**。
- **狭める変更（無効化を含む）は、途中で失敗しても前の listener を戻さない**（PR #829 のレビューで追加）。
  書き込みが残っているとき、狭めた設定の**保存**が失敗しても（ストレージのエラー、最後の再検証での拒否）、
  共通の巻き戻しには入らず、listener は閉じたままにする。結果は「閉じたまま・保存されていない」:
  `applyFailure` は元の理由（`saveFailed` など）/ `leftClosed`、監査は `failed` で `saved: false`・
  `restoredPrevious: false`・`listening: false`。`leftClosed` で保存済みなのは、理由が `writesRemaining` の
  ときだけ。書き込みが残っていないときの失敗は、今までどおり前の listener を戻す。
- 残った書き込みは `ServerSlot` が持ち続ける（`LeftoverWrites`）。次の適用は、listener を起動する前に同じ
  上限でもう一度待ち、まだ残っていれば上と同じ規則で断る。前の listener を戻した後も追い続ける。
- 監査の `detail.remainingWrites` は `{count, operations}`（`count` は全部の合計。`operations` は `METHOD path` の
  一覧で、止めた listener がいくつあっても全体で 8 件まで）。
- 「旧い世代が以後書けない保証」（世代の番号で全書き込みを柵で囲う）は採らない。サービス層の全部に手が入る。

### 6. Tauri のコマンドに層は要らない

Tauri の async コマンドは、Tauri が 1 つずつ別のタスクとして走らせる（`tauri` 2.12 の
`InvokeResolver::respond_async` が `async_runtime::spawn` する。確認済み）。webview が閉じても、コマンドの
future は捨てられない。これは輸送の違いで、認可と監査の対称（conventions §1）は変わらない。

### 7. 上限: 新規の受付の数だけ。1 件の時間には置かない

- **同時に走る書き込みは 256 件まで**（`MAX_DETACHED_WRITES`。PR #829 のクロスレビューで変更）。層が無いとき、
  同時に走る handler は開いている接続の数で抑えられていた。切り離した後は、送ってすぐ切るクライアントの仕事が
  接続の数の外に残るので、同じではない。上限に達している間に届いた書き込みは、handler を始めずに **503**
  （`kind: other`、「処理中の操作が多いため…」）で断り、`eprintln!` に残す。**受理済みの書き込みは止めない**。
  256 は、この種のアプリの通常の同時数よりずっと上に置いた値（書き込み 1 件は短い）。
- **枠は listener の世代をまたいで共有する**（`WriteBudget`。PR #829 の再レビューで追加）。停止の門と、
  世代ごとの数え上げ・待ち（drain）は listener ごとのままで、新規の受付の残り枠だけを共有する。止めた listener に
  残った書き込みは、終わるまで枠を使い続ける。再設定を断って前の構成を戻したときも、戻した listener が始められる
  のは残りの枠だけで、旧い書き込みが終わると枠が戻る。`RunningServer::write_budget()` で取り出し、
  `BoundServer::with_write_budget()` で次の listener に渡す（テンプレートは `ServerSlot` が 1 つ持つ）。渡さない
  listener は自分だけの枠を持つ。Tauri のコマンドは層を通らないので、この枠の対象ではない（§6）。
- **1 件の時間の上限は置かない**。途中で打ち切ることが、この ADR の防ぎたいことそのもの。長い書き込み
  （バックアップの作成）は切断の後も走り続け、終わる。止まらない書き込みは、停止のとき「残っている」として
  見える。

### 8. 終了

- ヘッドレス（`banto-serve`）: Ctrl-C で `stop()` を呼び、上限まで待つ。残っていればログに残して終える。
- デスクトップ: 今の終了は埋め込みのサーバーを止めていない（プロセスが消える）。Tauri のコマンドも同じ
  条件なので、この PR では変えない。DB のトランザクションは確定か取り消しのどちらかで、プロセスが消えた後に
  書くものは無い。「終了の前に待つ」を足すなら、コマンドの側も含めて別に決める。

## 検討した代替案

- **関数 `run_detached(label, work)` を handler ごとに呼ぶ**（下流の今の形）: 包み忘れが残る。不採用。
- **除外の口（メソッドや経路で外す）**: 外したい書き込みが今は無く、口があると外し忘れと同じ穴になる。不採用
  （決定 8）。
- **書き込みの本体を層で先に読み切ってから切り離す**: 認証の前に本体をためることになり、大きさの上限
  （extractor の側にある）を層がもう一度持つ必要が出る。不採用。本体の途中で切れた要求は何も起こさないので足りる。
- **停止で残った書き込みを中断する**: 途中で止まる。不採用。
- **同時に走る数に上限を置かない**（初版の案）: 切断した後の仕事は接続の数の外に残るので、「今までと同じ」では
  なかった。不採用（クロスレビュー）。
- **上限を超えても待ち続ける**: 設定の切り替えと終了が、終わらない書き込みに人質に取られる（Issue #283 と同じ形）。不採用。
- **狭める変更でも前の listener を戻す**: fail-open。不採用（計画書 §10 の 17）。
- **世代の番号で全書き込みを囲う**: サービス層の全部に手が入る。不採用。

## 帰結

- 切断しても、読めた書き込みは作成・失効・監査まで終わる。派生アプリは何もしなくてよい。
- 挙動の変化: (1) 切断で書き込みが止まらない。(2) handler の panic が、接続の切断ではなく 500 になる。
  (3) 停止中と、同時に走る書き込みが上限（256 件）のときの書き込みは 503。(4) `RunningServer::stop()` が `StopOutcome` を返す。(5) デスクトップの
  「LAN 設定の適用」が、書き込みが残っているときに失敗しうる（`writesRemaining`）。
- 層が入っても、handler の中の順序が悪ければ穴は残る。handler ごとの点検（確定 → 失効 → 監査の順、失効した
  後のセッションで走り続ける仕事が書かないこと）は **S2**（計画書 §7）。
- 試験: `crates/banto-server/tests/detach_writes.rs`（切断しても 2 段目まで走る／GET は今も捨てられる／panic は
  500／停止は走っている書き込みを待つ／終わらない書き込みは「残っている」）、`detach.rs` の単体（門を閉じた後は
  503 で handler が走らない）、`exposure.rs` の単体（向き。混ざった変更は狭める側）、
  `apps/admin-template/core/src/rest/tests/detach.rs`（実物の `POST /api/users` で、切断しても作成と監査が残る）、
  `apps/admin-template/src-tauri/src/tests/server_writes.rs`（再設定の 2 方向）。

## オーナーに確かめたい点

1. 停止時に待つ上限 **10 秒**（接続の 5 秒と並行）。バックアップの作成のような長い書き込みの最中に LAN 設定を
   変えると、広げる変更は失敗して「もう一度」になる。
2. panic と停止中の応答は、新しい kind を足さず `other`（500 / 503）にする。
3. 同時に走る書き込みの上限 256 件（新規の受付だけを断る）と、1 件の時間に上限を置かないこと（§7）。
4. 狭める変更で listener が要るとき、保存したうえで**エラー**で返す（`leftClosed`。画面はエラーの文言を出す）。
5. デスクトップの終了は今のまま（§8）。
