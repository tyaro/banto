## コンテキスト

下流（banto-industrial）から 3 件の要望が来た。根は同じ所にある。

- **#790**: 持ち主を username で識別している所が 3 層にある（サーバーの `ui.{username}.{key}`、wire の
  `Identity.id`、画面の `account:${id}`。`packages/admin-core/src/sessionController.svelte.ts:207-217`）。
  username は再利用できるので、消したアカウントと同名で作り直した別人が、前の人の記憶（一覧の記憶・最近の
  コマンド・ドックの配置）を引き継ぐ。`users.id` は同じ DB の中では再利用されないが、DB を作り直すと 1 から
  数え直し、**バックアップの復元でも巻き戻る**（採番の履歴も DB の中にある）。
- **#778**: ログインなし（Tauri の `auth.disabled`、合成セッション `local`）と、管理者相当の grant の操作は、
  監査の actor が行を持たない固定の名前（`local` など）で残る。ユーザー一覧のどの行とも結び付かない。
- **#786**: ui-settings の条件付きの書き込み。保存先の表を作り直すので、持ち主の表し方を一緒に決める必要がある。

2026-11-22 にオーナーが前提を変えた（決定 16〜18）: **次のメジャー（v8.0.0）は互換不要で、DB は 1 から作り直す**。
既存の DB・既存のデータは読まない。組み込みのユーザーは小文字の `admin`。初回セットアップでユーザーもパスワードも
作らない。これで、既存の行への埋め込み・旧い保存の移し替え・既存の `Admin` / `admin` アカウントの検出と改名が
すべて要らなくなり、設計が小さくなった。この ADR はその決定と、計画書が「C0 の ADR で確定する」と残した細目を記録する。

## 決定

### 1. 持ち主の識別: `users.account_uid` と wire の `accountId`

- アカウントの作成時に、サービス層が 128 bit の乱数（OS の乱数源、文字列）を `users.account_uid` に入れる。
  一意制約。改名・ロールの変更では変えない。**秘密ではない**（認証にも認可にも使わない。記憶を仕切る名前）。
  アカウントの行では列の制約で必須、組み込みの行には持たせない（§2）。
- wire の `Identity`（`crates/banto-server/src/auth/session.rs:27`）に `accountId` を足す（REST の
  `/api/auth/identity`・ログインの応答、Tauri のコマンド）。アカウントのセッションでは `account_uid`。
  grant セッションと Tauri のログインなし（`local`）には載せない。
- 画面の `sessionOwnerKey`: `local` と grant の kind は今のまま。アカウントは **`acct:<accountId>`**。
  `accountId` が無ければ **`null`**（何とも一致しない。fail closed）。dev ビルドでは、account の kind で
  `null` を返したときに 1 回だけ警告する。
- **`Identity.id` は username のまま**（監査の主体・画面の表示・`acting_username` の呼び手を変えない）。
- `instance.id` と `Identity.instanceId` は置かない。DB の中の値は復元で採番と一緒に巻き戻り、復元後に作った
  別人が同じキーを得るため。
- サーバーの中で持ち主を指す所（`ui_settings`、監査の `actor_id`）は `users.id` を使う。同じ DB の行どうしは
  復元しても一緒に戻るので食い違わない。画面の側（ブラウザーの保存）は DB と一緒に戻らないので `account_uid` を使う。

### 2. 組み込みのユーザー `admin`

- 新しい DB には、migration が入れた行が最初から 1 つ居る: `username = 'admin'`（小文字）・`kind = 'builtin'`・
  `role = 'admin'`・`password_hash` は NULL・`account_uid` は NULL。
  - 列の CHECK で「`kind = 'builtin'` ⇔ `password_hash IS NULL`」「`kind = 'builtin'` ⇔ `account_uid IS NULL`」を守る。
  - 組み込みの行は 1 つだけ、を部分一意インデックス（`WHERE kind = 'builtin'`）で守る。
- **パスワードを持たず、ログインできない**。credential verifier は `kind = 'account'` の行だけを照合の対象にする
  （列の CHECK と二重の守り）。組み込みの行に当たったときも、居ないユーザーと同じダミーのハッシュ検証を回す
  （応答の時間で見分けさせない）。`admin` へのログインの試行は、居ないユーザーと同じ扱いで、REST のログイン試行の
  制限にそのまま掛かる。
- **改名・無効化・降格・パスワードの設定・削除をすべて禁じる**（サービス層で。conventions §2）。
  `change_password`・`reset_password`・更新・削除の SQL にも `kind = 'account'` を入れる。
- **保護は、行を入れるのと同じ PR（C1）で有効にする**（クロスレビューの指摘 3）。行だけ先に入ると、その間の main で
  組み込みの行を消せる・照合で落ちる:
  - 今の削除（`crates/banto-admin-services/src/users.rs:1484-1508`）は、ほかに管理者が居れば対象の行をそのまま消す。
    CHECK と部分一意インデックスは削除を防がない。消えた行を後の PR は入れ直せない（適用済みの migration は再実行されない）。
  - 今の verifier はハッシュを非 NULL の型で読む（`users.rs:860-864`）。NULL の行に当たると読み取りが失敗する。
  - **C1 で入れる最低限**: (a) verifier の SELECT を `kind = 'account'` に絞る、(b) `change_password`・
    `reset_password`・更新（改名・ロール・無効化）・削除・CSV の取り込みが `kind = 'builtin'` を断る（サービス層の検査と
    SQL の条件の両方）。
  - C2 に残すのは、予約名（§4）・起動時の検査・帰属の印と `actor_id`（§3）・拒否の監査の両経路の対称。
  - **通常のアカウントは、C1 の後も今のまま作れる**（作成・初回セットアップ・ログイン。初回セットアップは C2b で消すまで
    残る）。組み込みの行だけがある DB で、初回セットアップと通常の作成が通ることを、SQLite と PostgreSQL の両方の
    試験で固定する。
- **最後の管理者のガード**（`ensure_admin_removal_allowed`、`users.rs:313`）は
  組み込みの行を数えない（`role = 'admin' AND kind = 'account'`）。数えると、人の管理者を全部消せてしまう。
- 行の `role` は一覧の表示だけで、**認可の判定には使わない**。
- **数える所と見せる所を分ける**（表示の契約）。**組み込みかどうかの判定は、どこでも名前ではなく `kind`**。
  - **数える・書き出す・照合する所は `kind = 'account'` だけ**: アカウントの件数、CSV の書き出しと取り込み、
    バックアップの検証、最後の管理者のガード、`has_admin`、credential verifier、自動ログインの対象、
    派生アプリが「ユーザーを選ぶ」ために引く一覧。
  - **管理のユーザー一覧だけが、組み込みの行を読み取り専用の 1 行として返す**。一覧の応答（`UserSummary`）に `kind` を
    載せ、画面は `kind = 'builtin'` の行に編集・削除・パスワードの操作を出さない（出しても、サービス層が断る）。
    この一覧のページングの総数は、見せている行の数（組み込みの行を含む）。
- 組み込みの行が無い・2 つ以上ある DB（直接の編集でしか起きない）は、起動時に明示のエラーで止める。入れ直さない。
- 行にするのは `admin` だけ。`public` などほかの grant の固定 identity は行を作らない（§4 で予約名にする）。

### 3. ログインなしの操作の帰属: 明示の印 `audit_as_builtin_admin`

どのセッションを `admin` に帰属させるかは、id・name から推測しない（conventions §10）。配線の層が付ける印で決める。

- **印の名前（この ADR で確定）**: `GrantSpec`（`crates/banto-server/src/grant.rs:197`）に
  **`audit_as_builtin_admin: bool`** を足す。既定は `false`（`GrantSpec::new` が入れる）。
  名前に `audit` を入れるのは、効くのが**監査の帰属だけ**だと読めるようにするため（認可・ロール・持ち主のキーは変えない）。
- **載せる場所（この ADR で確定）**: 印は `GrantSpec` → 発行時の **`TokenRecord`** → `AuthenticatedSession`
  （`crates/banto-server/src/auth/session.rs:146`。`#[serde(skip)]`）の順に写す。
  - REST はトークンの発行時に `TokenRecord` を保存し（`crates/banto-server/src/auth/state.rs:483`）、リクエストごとに
    そこからセッションを組み直す（`state.rs:840-863`）。`AuthenticatedSession` に欄を足すだけでは、組み直しで消える。
    持ち続けるのは `TokenRecord`。
  - 計画書 §4.3 は「`SessionStamp` に写す」と書いたが、`SessionStamp`（`session.rs:53`）はアカウントの
    `account_id` と `auth_epoch` の組で、grant セッションでは `None`（`session.rs:137`）なので載せられない。
  - 印は wire に出さない（`Identity` の id・name・role と `kind` は変えない）。
- **監査の主体は、認可に使ったスナップショットを最後まで渡す**（クロスレビューの指摘 4）。
  - 認可のガード（`require_auth` / `require_role_at_least`）が、通したセッションから監査の主体
    （`AuditActor`: `actor_username`・`actor_id`・`actor_role`・`actor_kind`）を **1 回だけ**作り、リクエストに付ける。
    handler は、それを成功の監査にも拒否の監査にも渡す。
  - **監査を書く所で、bearer からもう一度引かない**。今の `actor_identity` / `record_write`
    （`crates/banto-server/src/routes/mod.rs:98-99`・`:179-196`）は、認可とは別の時点でトークンを引き直して bare の
    `Identity` を得る。この経路では印も内部の id も落ち、処理の間にトークンが失効していれば主体そのものが取れない。
    スナップショットを渡せば、処理の後に失効していても、監査は認可した時点の主体で残る。
  - ガードがロールの不足で拒むときは、同じスナップショットで拒否の監査を書く。認証そのものに失敗したとき
    （トークンが無い・無効）は、主体なしのまま（今のまま）。
  - Tauri のコマンドも、同じ型と同じ関数でスナップショットを作って渡す（conventions §1）。
- **帰属を決める関数は 1 つ**にし、REST と Tauri の両方がそれを呼ぶ。見るのは印だけ。
  - 印つき: `actor_username = 'admin'`、`actor_id` = 組み込みの行の id。`actor_role` は**そのセッションの実際の
    ロール**（viewer なら viewer）。組み込みの行の id は、配線が起動時に 1 回 `kind = 'builtin'` で引いて持つ
    （名前でも固定の数でも引かない。復元は再起動を伴うので食い違わない）。
  - 印なしの grant（閲覧公開の `public` など）: 今のまま固定 id を書き、`actor_id` は NULL。
  - アカウント: `actor_username` は username、`actor_id` は `users.id`。
- **経路は `actor_kind` に残す**（wire は `actorKind`）。actor が `admin` の行は複数の経路から来るので、actor だけでは
  経路が分からない。既にある `origin` は REST と Tauri を分けるが、同じ REST の中の複数の印つき grant は分けられない。
  - 値: `account` / `local`（Tauri のログインなし）/ `grant:<kind>` / `cli`（§7）。主体の無い行は NULL。
  - **認可には使わない**（記録だけ。conventions §10 は変えない）。**トークンの値は残さない**。
- **Tauri のログインなし（`local`）は `admin` に帰属させる**。Tauri の配線が、合成セッションに同じ意味の印を付ける
  （監査の actor は `local` から `admin` に変わり、`actor_kind = 'local'`）。ui-settings の持ち主と `sessionOwnerKey` は
  `local` のまま（帰属は監査だけ）。
- 印を付けた grant に、ロールや `require_loopback_peer` の条件を banto は足さない（どの grant を `admin` の操作として
  残すかはアプリの判断）。管理者相当の grant の既定（loopback・小さい `max_sessions`）は ADR-0017 の帰結のまま。
- 監査の表に `actor_id`（NULL 可、外部キーなし。ユーザーを消しても監査は残す）と `actor_kind`（NULL 可）を足す。
  `actor_username` のスナップショットは残す。

### 4. 予約名と、サービス層へ渡す口

- **予約するもの**: `admin` と、登録した grant の固定 id（`GrantSpec.identity.id`。テンプレートでは `public`、
  `grant.rs:83`）。アカウントの作成・改名で、**大小無視**で断る（`Admin`・`ADMIN` を作って見分けにくくするのを防ぐ）。
  比較は Rust の側で、両方を `to_lowercase()` して行う（`users.username` の一意制約は大小を区別するままで、
  DB の照合順序には頼らない）。`local` は予約しない（新しい持ち主の表し方では衝突しない）。
- **予約は見分けやすさのため**で、判定の根拠にしない（conventions §10 は変えない）。
- **渡す口（この ADR で確定）**: grant は派生アプリが足せる開いた集合で、サービス層は axum / tauri を知らない
  （conventions §2）。そこで:
  - `banto-admin-services` に、文字列の集合を包む小さい型 `ReservedUsernames` を置く。
  - `UsersService` に **`with_reserved_usernames(self, ReservedUsernames) -> Self`** を足す。既にある
    `with_permission_catalog`（`crates/banto-admin-services/src/users.rs:499`）と同じ、構築時の builder の形。
    `UsersService::new` の引数は変えない。
  - **`admin` はサービス層が自分で必ず予約する**（組み込みの行を知っているのはサービス層。配線が渡し忘れても外れない）。
    配線が渡すのは grant の固定 id だけ。
  - `GrantRegistry` に、登録済みの固定 id を列挙する読み取りの口を足す。配線の層（REST の `banto-serve` と
    Tauri の `lib.rs` の両方）が、それを `ReservedUsernames` に入れて渡す。
- **起動時の検査（N6）**: `UsersService` に、予約名と `kind = 'account'` の username を大小無視で照らす 1 文の検査を置き、
  両方の配線が起動時に呼ぶ。当たるのは「grant を後から足したら、その固定 id と同名のアカウントが既に居た」場合だけ。
  当たれば、名前と対処（そのアカウントを作り直すか、grant の固定 id を変える）を書いたエラーで**起動を止める**。
  改名の口は作らない。

### 5. 初回セットアップの撤去と、新しい DB の既定

- **初回セットアップでユーザーもパスワードも作らない**。新しい DB はユーザーを作らずに起動する。
- **ログインなしの既定は、新しい DB だけ**（クロスレビューの指摘 1）。基準の migration（`0014`）が、`settings` に
  `auth.disabled = 'true'` と `auth.disabled_role = 'admin'` を**明示して入れる**。Tauri は起動すると合成セッション
  `local`（ロールは `auth.disabled_role`）でアプリに入る。ログインの画面も初回セットアップの画面も出ない。
- **キーが無い・値が読めないときは、既定で埋めずに起動を止める**。壊れた設定から、admin 相当のローカルセッションを
  自動で作らない（fail closed）。
  - `auth.disabled` が無い、または `true` / `false` 以外。
  - `auth.disabled` が on なのに、`auth.disabled_role`（合成セッションを組む値）が無い、または知らない値。
    今の `auth_config` は、読めないロールを admin に落とす（`crates/banto-admin-services/src/settings.rs:540-556`）。
    これをやめる。
  - 保存（`set_auth_config`）は関係するキーを同じトランザクションで全部書くので、アプリの操作では欠けない。
    当たるのは直接の編集と破損だけ。復旧は §7 の CLI（ログイン必須に書き直す）か、§9 の復元。
  - 計画書 §4.3 の「`auth.disabled` の既定を on に変える（キーが無いとき）」は採らない。コードの既定を on にすると、
    v8 の DB でキーが消えただけで、端末の前の誰でも管理者になれる。
- **初回の seed の条件は、0014 と同じ PR（C1）で直す**（再レビューの指摘 1）。`seed_first_boot_settings` は
  「`settings` が空のとき」だけ書く（`apps/admin-template/core/src/first_boot.rs:40-53`）。0014 が `settings` に
  行を入れると、新しい DB でもこの条件が成り立たない。display の scaffold はこの経路で `server.viewer_public`・
  `server.enabled`・`server.bind` を入れる（`scripts/scaffold.mjs:2026-2032`）ので、seed を直さずに 0014 だけが入ると、
  display の生成物は公開閲覧なしで起動する。`settings` を空で作る今のユニットテストからは見えない。
  認証のキーの INSERT を後ろの PR へ回す案は採らない（基準の migration を 2 回書き換えることになる）。
  - **契約**: seed は**新しい DB の最初の起動で 1 回だけ**書く。migration が入れた行が既にあっても書き、同じキーは
    seed の値で上書きする（プリセットの既定が migration の既定に勝つ）。2 回目以降の起動では何も書かない
    （利用者が変えた設定を戻さない）。
  - **形**: 判定を「表が空」から「seed 済みの印が無い」に変える。印は `settings` の 1 行で、seed の各行と同じ
    トランザクションで書く（途中で落ちて半分だけ入った状態を作らない）。印のキー名は C1 で決める。
    印は DB の中にあるので、復元すれば一緒に戻る（seed 済みの DB のバックアップは、復元の後に seed し直されない）。
  - 順序は今のまま「予約の適用 → migration → seed → 設定の読み取り」（`banto-serve.rs:111-142`、
    `src-tauri/src/lib.rs:4358-4391`）。C2b で入る設定の検査（上）は seed の後に走る。
  - C1 の完了条件: **C1 の実 migration（0001〜0014）を当てた DB** で display の生成物を起動し、公開閲覧が有効に
    なること（§10）。
- ユーザー管理が要る利用者だけが、ユーザー管理の画面からアカウントを作る。その操作の監査の actor は `admin`（§3）。
- 消すもの: `setup_first_user`・`is_initialized`（`users.rs:738`・`:706`）、REST の `POST /api/auth/setup`・
  `allow_setup`・status の `initialized`、Tauri の `auth_setup` と `auth_config_apply` の bootstrap の窓、
  画面の `setup` の分岐と `AuthProvider.setup`、`BANTO_ALLOW_SETUP`。「初期化済み」という状態そのものが無くなる
  （新しい DB は migration の後、いつでも使える）。

### 6. ロックダウンの条件と、安全の前提

- **安全の前提**（ADR-0017・spec M11 の考え方のまま）: ログインなしの間は、**その端末の前に居る人を信用する**。
  誰でも、合成セッションのロール（既定は admin）で操作できる。これが許されるのは、
  **ログインなしの間は、ネットワークから業務・管理のデータを変えられない**から。
- **この前提は、次の 4 つで守る**（クロスレビューの指摘 1）。`auth_server_combination_allowed`
  （`crates/banto-admin-services/src/settings.rs:237`）だけでは守れない: あの関数は起動と保存の組み合わせを見るだけで、
  認証済みの REST の書き込みは止めない。`banto-serve` は保存した `server.enabled` ではなく `BANTO_BIND` / `PORT` で
  listen する（`apps/admin-template/core/src/bin/banto-serve.rs:83`・`:277`）。
  1. **合成セッション `local` は Tauri のプロセスの中だけ**。REST はログインなしの管理者のセッションを発行しない（今のまま）。
  2. **ログインなしの間（`auth.disabled` = on）、REST は読み取り専用**。アカウントのログインを断る（資格情報が正しくても）。
     ログインなしへ切り替える保存の直後に、同じ関数の中でアカウントのトークンを全部失効させる（ADR-0017 の
     「保存 → 同じ関数の中で失効」と同じ形）。届くのは、閲覧公開（viewer）と、派生アプリが明示して登録した grant だけ。
  3. **listen の条件は、両方の配線が同じ関数で見る**。Tauri は今のまま（「`auth.disabled` かつ `server.enabled`」は
     閲覧公開が on のときだけ。保存の両側と起動時）。`banto-serve` は常に listen するので、起動時に同じ関数を
     `server_enabled = true` として呼ぶ。ログインなしで閲覧公開も off なら、**listen せずに明示のエラーで止まり**、
     §7 の CLI を案内する。
  4. **LAN から操作させたい利用者は、先に管理者のアカウントを作ってロックダウンする**。この規則は緩めない。
- **ログインの許可・トークンの発行・トークンでの認可は、モードの切り替えと直列にする**（再レビューの指摘 3。
  C2b の実装条件）。上の 2 の「入口でログインを断る + 切り替えの直後に全部失効」だけでは、次の順で穴が残る:
  入口の判定を通る → 資格情報の照合を await している間にログインなしへ切り替わり、トークンが全部失効する →
  古い照合が終わってトークンを発行する。今の `login_rate_limited` は照合を await した後に発行する
  （`crates/banto-server/src/auth/state.rs:348-390`）。
  - **モードの世代**: `AuthState` が、今のモード（ログイン必須 / ログインなし）と、切り替えのたびに進む世代を持つ。
    切り替えは、トークンの表と同じロックの中で「世代を進める + アカウントのトークンを全部失効」を 1 度に行う。
    形は grant の世代のガード（`grant_generation` / `issue_grant_token`。`auth/state.rs:438-515`、ADR-0017 §2）と同じ。
  - **発行**: ログインは入口で世代を読む。照合の後、発行の直前に、同じロックの中で「世代が入口と同じ」かつ
    「今のモードがログイン必須」を確かめる。違えば発行せずに断る（資格情報が正しくても）。トークンは発行時の世代を持つ。
  - **認可**: アカウントのトークンでの認可は、**認可が終わる時点**でも同じ世代を確かめる。今の経路は、DB の照合を
    await した後に、照合の前に読んだセッションを返す（`auth/state.rs:690-714`）。`refresh_identity`（`:817-824`）は
    stamp が同じなら身元を書き戻す。照合の間に切り替えで失効したトークンが、この 1 回だけ通りうる。照合の後に
    「トークンがまだ表にあり、その世代が今の世代と同じ」を確かめ、違えば未認証として扱う。
  - **契約**: 切り替えが終わった後は、旧い世代から発行も利用もできない。ロックダウン（ログインなし → ログイン必須）も
    同じ世代を進める（合成セッションと、ロックダウンで閉じる grant の失効は下のとおり）。
  - **進行中の書き込み**: 「許可済み」とみなす時点は、**世代の確認つきの認可が終わった時点**（ガードが §3 の主体の
    スナップショットを作った時点）。そこを通った書き込みは、切り替えで中断せず、認可した時点の主体で最後まで走る
    （#793 の層が切り離した仕事と同じ扱い。計画書 §4.5）。切り替えの後に認可が終わる要求は断る。切り替えが残った
    仕事を待つか・監査にどう残すかは #793（S1・S2、ADR-0035）の「失効と監査の順」の決め方にそろえ、C2b で固定する。
  - **回帰試験**: 照合（verifier）を意図的に止めている間に切り替えを終わらせ、照合を再開しても、トークンが
    発行されないこと。認可の DB 照合を止めている間に切り替えを終わらせ、その要求が通らないこと（§10）。- **「読み取り専用」が禁じるもの・禁じないもの**:
  - 禁じる: 業務データと管理の変更（リソース・添付・ユーザー・設定・バックアップなど、viewer を超えるロールや権限が
    要る操作の全部）。
  - 禁じない (a): 閲覧公開のセッションが、**自分の kind の ui-settings を PUT する**こと（`/api/ui-settings/*` は
    `require_auth` だけ。`crates/banto-server/src/routes/ui_settings.rs:59-71`。保存先は §8 の `grant:publicViewer`）。
    表示の好みで、業務・管理のデータではない。今のまま。
  - 禁じない (b): **派生アプリが明示して登録した grant** が、その `GrantSpec` のロールと権限で行う操作（ADR-0017）。
    発行の条件はアプリの責任で、ロックダウンで閉じる grant は下のとおり失効する。
- **Tauri のログインなしの間に、既にあるものができること**:
  - 既存のアカウント: 行は残り、ユーザー管理の画面で管理できる。そのアカウントでのログインは、Tauri の画面からも
    REST からもできない（画面は `local` で入る。REST は上の 2）。
  - 旧いトークン: ログインなしへ切り替えた時点で失効する。トークンはメモリの上だけなので、再起動でも残らない。
  - grant: 閲覧公開は読み取りと自分の kind の ui-settings だけ。アプリの grant は、その発行の条件のまま。
- **アカウントが 0 の間の REST**: ログインは必ず失敗し（アカウントが無い。組み込みは拒む）、初回セットアップの口も
  無いので、届くのは閲覧公開の読み取りと、派生アプリが足した grant だけ。認可の規則は両経路で同じ関数を通る
  （conventions §1）。
- **ロックダウン**（`auth.disabled` を off にする）は、**ログインできる管理者のアカウント
  （`kind = 'account' AND role = 'admin'`）が 1 つ以上あるときだけ**許す。無ければ `Validation` で断り、
  「先に管理者のアカウントを作ってください」と返す。
  - 判定と保存は同じロックの中で行い、ADR-0017 の流れ「保存 → 同じ関数の中で直後に grant の失効」の**手前**に判定を置く。
  - ロックダウンの後、ログインなしのセッションは失効する。grant の失効は ADR-0017 のまま: 発行の条件が
    ロックダウンで閉じる grant（派生アプリの試運転など）は、保存の直後に同じ関数の中で `revoke_grant_tokens(kind)` を呼ぶ。
- **最後の管理者のガードは、ログインなしの間も常に掛ける**（N5）。1 つ作った管理者は 0 に戻せないので、
  「判定の後・保存の前に最後の管理者が消える」競合が起きない。代わりに、ログインなしの間に作った最後の管理者は消せない。
- **ログイン必須なのに管理者のアカウントが 0 の DB**（アプリの操作では作れない。直接の編集だけ）は、起動時に
  明示のエラーで止める（N4。Tauri も `banto-serve` も）。黙ってログインなしへ戻さない（DB を書き換えられる人が
  認証を外せる形になる。fail-open）。

### 7. ヘッドレスの最初のアカウントと、復旧の口

- ヘッドレス（`banto-serve` だけ。PostgreSQL の運用・e2e）は Tauri のログインなしを持たないので、最初のアカウントを
  **DB に触れる人のオフラインの CLI**（`banto-serve` のサブコマンド）で作る（N3）。ネットワーク越しの口にしない。
- **CLI の契約（この ADR で確定。クロスレビューの指摘 1）**: CLI は**管理者の作成とロックダウンを、1 回で安全に終える**。
  アカウントを作るだけでは、新しい DB の `auth.disabled = on` から「REST で書き込める状態」に至る手順が無い（§6 の 2・3）。
  - **待ち受けより前に処理し、その場で終了する**。ソケットを開かず、ルーターも組まない。終了コードで成否を返す。
  - **1 つのトランザクション**で、(a) 管理者のアカウントの作成、(b) `auth.disabled = false` の保存（ロックダウン）、
    (c) 監査の行、を書く。途中で失敗すれば何も残らない。「アカウントだけ」「ロックダウンだけ」の口は作らない
    （半端な状態を作らない）。既にログイン必須の DB では (b) は同じ値の書き直しになる（復旧と同じ口）。
  - アカウントを作る処理そのものは `UsersService` の普通の作成を通す（検証・予約名が同じ）。
  - migration を先に流すので、新しい DB にそのまま使える（旧版の DB は §9 のとおり断る）。§5・§6 の起動時の検査
    （設定のキーの欠落・破損、ログイン必須で管理者が 0）の**手前**で動く。その状態を直す口だから。
  - **予約された復元（`restore-pending.sqlite3`）があるときは、何も書かずに明示のエラーで止まる**（再レビューの
    指摘 2）。CLI は予約を暗黙に適用しないし、無視もしない。無視すると、CLI が成功した後の次の起動で予約が適用され、
    作ったアカウントとロックダウンが消える。エラーは「先に復元を適用する（アプリを起動する）か、予約のファイルを
    消してから、もう一度実行する」を案内する。どちらを先にするかは運用者が決める。
  - **アプリとサーバーを止めてから実行する**。動いているプロセスのメモリの上のセッションは、CLI からは失効できない。
    Tauri と同じ SQLite のファイルに使うと、そのアプリもログイン必須になる（意図どおり）。
  - 監査は組み込みの `admin` の操作として残す（`actor_kind = 'cli'`、`origin = 'cli'`）。
  - パスワードは引数で受けない（プロセスの一覧とシェルの履歴に残る）。標準入力から読む。引数の細目は C2b で決める。
- **ヘッドレスの最初の起動の道筋**: 新しい DB → `banto-serve` をそのまま起動すると、ログインなしで閲覧公開も off なので
  listen せずに止まる（§6 の 3）→ CLI（管理者の作成 + ロックダウン）→ 起動 → ログイン → 更新。
- **復旧の口（この ADR で確定。N4 の残り）**: この CLI は **`banto-serve` だけ**に置く。
  **Tauri の実行ファイルには CLI を持たせない**。
  - ログイン必須なのに管理者が 0 の状態・設定のキーの欠落は、DB を直接書き換えたときにしか起きない。そこまで出来る人は、
    同じ DB を指して `banto-serve` の CLI を使える（SQLite のファイルでも PostgreSQL でも同じ）。
    バックアップで戻す道は §9 のオフラインの手順（`banto-serve` が無い配布物でも使える）。
  - デスクトップの実行ファイルに「引数でアカウントを作る口」を足すと、認証を持つすべての配布物に、画面を通らない
    管理者の作成の口が増える。Windows の GUI の実行ファイルは標準入力・コンソールの扱いも別に要る。
  - 処理は core の関数 1 つにして `banto-serve` から呼ぶ。派生アプリが自分の実行ファイルに同じ口を足すことは妨げない。

### 8. grant セッションの ui-settings は kind をキーにする

- 保存先は新しい表 `ui_settings`。持ち主は文字列の列で、アカウントは `acct:<users.id>`、grant は
  **`grant:<kind>`**、Tauri のログインなしは `local`。grant のためにユーザーの行は作らない。
- 同じ kind の端末は設定を共有する（今の `ui.<identity.id>.*` と同じ性質。キーが固定 id から kind に変わる）。
  印つきの grant も `grant:<kind>` のまま（`admin` の持ち物にしない。帰属は監査だけ）。
- アカウントの行は別の列 `user_id` の外部キー（`ON DELETE CASCADE`）で守る。revision の形・条件付きの書き込みは
  #786 の範囲で、この ADR では決めない（計画書 §4.4）。

### 9. 互換不要・基準の作り直し

- **データの移行は無い**。既存の `0003_users.sql`・`0005_audit_log.sql` を新しい形に**書き換え**、
  `0014_ui_settings.sql`（表、組み込みの `admin` の行の INSERT、§5 の設定の INSERT）を足す（SQLite・PostgreSQL の両方。
  rule 11 の対称は保つ）。ほかの 11 本とファイル名・連番は変えない。
- conventions §11 の「リリース済みの migration は追記のみ」を **1 回だけ**破る。`pnpm verify:migrations` には、
  タグ `v7.11.0` と比べるときにこの 4 ファイルの変更だけを許す、今回かぎりの許可を書く（C1）。
  v8.0.0 のタグの後は、また追記のみ。
- **旧版の DB・バックアップは読まずに、明示のエラーで断る**。
  - 起動: 0003 の本文が変わるので、sqlx が適用済みの checksum の不一致（`VersionMismatch`）で止まる。0014 は連番の
    最後なので、新しい migration が旧版の DB に当たる前に止まる。`db::run_migrations`
    （`apps/admin-template/core/src/db.rs`）がこれを「この DB は v8.0.0 より前の版のものです。読めません。
    DB を作り直してください」に写す。
  - 復元: 置き換えの**前**に断る（下）。
- **復元の候補は、表の名前だけでなく migration の履歴で確かめる**（クロスレビューの指摘 2）。
  - 今の検査（`crates/banto-admin-services/src/backup.rs:292-317`）は `integrity_check` と必須の表の名前だけを見て、
    起動時の適用（`backup.rs:731-784`）が実ファイルを入れ替えた**後**に、通常の migration の検査が走る。
    必須の表が全部あり `integrity_check` が ok でも、v7 の checksum を持つファイルはこの検査を通る。
    通ると、入れ替えの後に `VersionMismatch` で起動できなくなる。`REQUIRED_TABLES`（`backup.rs:151`）に
    `ui_settings` を足すだけでは足りない（足すのは足す）。
  - **見るもの**: 候補を読み取り専用で開き、`_sqlx_migrations` を読む。(a) 全部の行が成功している、(b) 各行の版が
    このアプリの migrator にあり、checksum が一致する、(c) v8 の基準（`0001`〜`0014`）が全部適用済み。
    migrator に無い版（より新しい版のバックアップ）・checksum の不一致（旧版）・基準の欠けは断る。
    基準より後の未適用は許す（起動時の migration が前へ進める）。
  - **migrator は配線の層が渡す**。版と checksum の一覧（派生アプリが足した migration を含む）を知っているのはアプリで、
    サービス層ではない（conventions §2）。渡されていなければ、予約も適用も断る（fail closed）。
  - **2 回見る**: 予約のとき（ステージ）と、起動時の適用の直前（入れ替え・WAL の削除・適用前の自動バックアップの手前）。
    適用の直前に落ちたら、予約のファイルを消して適用をやめる。**元の DB には触らない**（今の、不正な予約ファイルの扱いと同じ）。
  - **回帰試験**: 必須の表が全部あり `integrity_check` が ok で、v7 の checksum を持つ候補が、(1) 予約で断られる、
    (2) 予約のファイルとして直接置いても、起動時に適用されず、元の DB のバイト列が変わらない、(3) その後の起動が通る。
    migrator に無い版を持つ候補・基準が欠けた候補も同じ。
- **復元の候補は、v8 の中の起動条件でも確かめる**（再レビューの指摘 2）。履歴の検査は v7 と知らない版を止めるが、
  履歴も `integrity_check` も正常な v8 の候補が、起動時の検査（§2 の組み込みの行、§5 の設定、§6 のログイン必須で
  管理者が 0）で止まることは防がない。その候補を入れ替えると、**正常だった元の DB が置き換わった後に**起動が止まる。
  - **見るもの**（入れ替えの前。読み取り専用）: 起動を止める検査の全部。(a) 組み込みの行がある
    （`kind = 'builtin'` の `admin` が 1 行）、(b) 必須の設定が読める（`auth.disabled` が `true` / `false`。on なら
    `auth.disabled_role` が知っている値）、(c) ログイン必須なら、ログインできる管理者
    （`kind = 'account' AND role = 'admin'`）が 1 つ以上、(d) 予約名と grant の固定 id の当たり（§4）。
  - **起動時の検査と同じ関数を使う**。条件を 2 か所に書かない。**起動を止める検査を足す PR は、同じ PR で復元前の
    検査にも掛ける**（組み込みの行と §4 の当たりは C2、設定と管理者は C2b）。これを各 PR の完了条件にする
    （計画書 §7）。検査の関数は配線の層が migrator と一緒に渡す（派生アプリの grant を知っているのはアプリ）。
  - **基準より後の未適用の migration がある候補**は、そのままでは起動時と同じ状態を読めない。候補を作業用の
    コピーに写し、コピーに migration を当て、同じ検査を通してから交換する。入れ替えるのは元の候補で、
    作業用のコピーは捨てる（migration は入れ替えの後の起動が、いつもどおり流す）。コピーへの migration が
    失敗したら断る。
  - **断ったときは、元の DB に触らない**（履歴の検査と同じ。予約のファイルを消して適用をやめる）。見る時期も同じ 2 回
    （予約のときと、適用の直前）。
  - **回帰試験**: 履歴と `integrity_check` が正常な v8 の候補で、`auth.disabled` の行が無いもの・ログイン必須で
    管理者が 0 のもの・組み込みの行が無いものが、予約でも適用の直前でも断られ、元の DB のバイト列が変わらず、
    その後の起動が通る。
- **オフラインの復旧手順**（起動が止まった後に「バックアップで戻す」道）。今の予約は、動いている管理の画面からしか
  作れない。起動が止まるとそこへ届かないので、画面を通らない手順を決めておく。
  - アプリを止める → 戻したいバックアップを、その DB のバックアップのディレクトリに予約のファイル名
    （`restore-pending.sqlite3`）で置く → 起動する。
  - **起動の順序は「予約の適用 → migration → 設定と管理者の検査」**（今も適用が先。`banto-serve.rs:111`、
    `apps/admin-template/src-tauri/src/lib.rs:4358`）。この順を規約として固定する。手で置いたファイルも、適用の直前の
    検査（上の 2 つ: 履歴と起動条件）を通る。落ちれば消され、元の DB は変わらない。seed（§5）は migration の後・
    設定の検査の前。§7 の CLI は、予約のファイルがあれば止まる（適用も無視もしない）。
  - `banto-serve` を同梱しない、デスクトップだけの派生アプリでも使える。手順は upgrading と README に書く（C1）。
  - PostgreSQL には banto の復元の口が無い（`backup.rs:206-215`）。運用者の道具で戻す。旧版の DB は、上の起動時の
    検査が断る。

### 10. 受け入れ試験（実装 PR の完了条件に入れる）

- **ヘッドレスの道筋**（C2b。SQLite と PostgreSQL の両方）: 新しい DB → そのまま起動すると listen せずに止まる →
  CLI（待ち受けを始めずに終了。アカウントとロックダウンと監査が 1 度に入る）→ 起動 → ログイン → 更新が通り、
  監査が残る。CLI が途中で失敗した DB には、アカウントもロックダウンも残らない。
- **Tauri のログインなしの間**（C2b）: 既存のアカウントで REST のログインができない。切り替えの前に発行した
  アカウントのトークンで REST の読み書きができない。閲覧公開のセッションは、読み取りと自分の kind の ui-settings の
  PUT だけができ、業務・管理の変更は拒まれる。明示のアプリ grant は、その `GrantSpec` のとおりに動く。
- **切り替えとの競合**（C2b）: 照合を止めている間にログインなしへ切り替えると、照合を再開してもトークンが
  発行されない。認可の DB 照合を止めている間に切り替えると、その要求は通らない。切り替えの前に認可が終わった
  書き込みは最後まで走り、監査は認可した時点の主体で残る（§6）。
- **初回の seed**（C1）: C1 の実 migration を当てた新しい DB で、display の生成物が `server.viewer_public`・
  `server.enabled`・bind を seed し、公開閲覧が有効になる。2 回目の起動は、利用者が変えた設定を上書きしない。
  seed が空のアプリは、今までどおり何も書かない（§5）。
- **設定の異常**（C2b）: `auth.disabled` が無い・読めない DB、ログインなしで `auth.disabled_role` が無い・読めない DB、
  ログイン必須で管理者が 0 の DB は、Tauri でも `banto-serve` でも起動が止まり、合成セッションを作らない。
  CLI で直る。
- **組み込みの行の保護**（C1。両方言）: 行が入った時点で、削除・更新・パスワードの設定・ログインが拒まれる。
  通常のアカウントの作成と初回セットアップは通る。管理のユーザー一覧は組み込みの行を返し、件数・CSV・`has_admin` は
  数えない。
- **監査の主体**（C2）: 印つきの grant の成功と拒否の監査が、REST と Tauri で同じ actor・`actor_id`・`actor_kind` に
  なる。認可の後・監査の前にトークンを失効させても、監査は認可した時点の主体で残る。`actor_kind` で、`local` と
  kind の違う 2 つの印つき grant と `cli` を見分けられる。監査にトークンの値が出ない。
- **復元**（C1）: §9 の履歴の回帰試験。起動条件の回帰試験は、その条件が入る PR で足す（組み込みの行と
  §4 の当たりは C2、設定と管理者は C2b）。
- **CLI と予約された復元**（C2b）: 予約のファイルがある DB で CLI を実行すると、何も書かずに明示のエラーで終わり、
  予約のファイルも DB も変わらない。

## 検討した代替案

- **持ち主のキー**
  - **採用: アカウントごとの乱数 `account_uid`。** 復元にも作り直しにも強い。
  - 不採用: `users.id` をそのまま使う。DB の作り直しと復元で同じ値が別人に渡る。
  - 不採用: `instance.id` + `users.id`。`instance.id` を DB に置くと復元で一緒に巻き戻り、同じ穴が残る。
  - 不採用: `Identity.id` を username から替える。監査・表示・`acting_username` の呼び手が全部変わる。
- **組み込みのユーザー**（N1）
  - **採用: ログインできない行。ログインなしの操作の記録先だけ。初回セットアップも無くす。**
  - 不採用: パスワードでログインできる `admin`（初回セットアップでパスワードを決める）。既知の名前がパスワードの
    的になり、最後の管理者のガード・verifier・`password_hash` に組み込みの行のための分岐が要る。
  - 不採用: 名前を `Admin` や内部名 `builtin.admin` にする。決定 17 で小文字の `admin` に確定。
- **帰属の決め方**
  - **採用: `GrantSpec` の明示の印を `TokenRecord` とセッションに写し、認可に使った主体のスナップショットを監査へ渡す。**
  - 不採用: 固定 id やロールから推測する（「admin ロールの grant は `admin`」など）。conventions §10 に反し、
    派生アプリが grant を足すと黙って帰属が変わる。
  - 不採用: 印を `SessionStamp` に載せる。grant セッションは `SessionStamp` を持たない（§3）。
  - 不採用: 印の名前を `acts_as_builtin_admin` などにする。認可も変わるように読める。
  - 不採用: 印を `AuthenticatedSession` だけに足し、監査を書く所で bearer から引き直す（今の形）。REST は
    リクエストごとに `TokenRecord` からセッションを組み直すので印が消え、処理の間に失効すれば主体も取れない（§3）。
  - 不採用: 経路を残さない。actor が `admin` の行の出どころ（Tauri のログインなし・どの grant・CLI）を後から追えない。
    `origin` は REST と Tauri しか分けない。
- **予約名を渡す口**
  - **採用: `UsersService::with_reserved_usernames`（builder）。`admin` はサービス層が自分で予約。**
  - 不採用: `UsersService::new` の引数に足す。呼び手（試験を含む）を全部書き換える。渡し忘れは builder でも
    起きるが、`admin` だけは外れない形にしたので、残る穴は grant の固定 id の見分けにくさだけ。
  - 不採用: 作成・改名の操作ごとに一覧を引数で渡す。REST と Tauri の呼び手が別々に組み立てることになり、対称が崩れやすい。
  - 不採用: サービス層が `GrantRegistry` を読む。`banto-admin-services` が `banto-server` に依存する（conventions §2）。
- **migration の形**（N2）
  - **採用: 基準を作り直す（0003・0005 を書き換え、0014 を足す）。** 旧版の DB を sqlx が自分で断り、
    列の制約を最初から正しく置ける。
  - 不採用: 0014 を足すだけ。規約は破らないが、旧版の DB に 0014 がそのまま当たるので自前の検査が要り、
    SQLite の `ALTER TABLE` では `account_uid` を必須にできず、`password_hash` の `NOT NULL` も外せない。
  - 不採用: 全部を 1〜数本に畳み直す。scaffold・レシピ・README がファイル名を引いている所を全部直すことになる。
- **ヘッドレスの最初のアカウント**（N3）
  - **採用: DB に触れる人のオフラインの CLI。管理者の作成とロックダウンを 1 つのトランザクションで終え、
    待ち受けを始めずに終了する。**
  - 不採用: CLI はアカウントを作るだけにする。新しい DB の `auth.disabled = on` から、REST で書き込める状態に
    至る手順が無い。ロックダウンを別の口にすると、片方だけ済んだ半端な状態ができる。
  - 不採用: `banto-serve` だけ `auth.disabled` を見ず、常に認証必須として動かす。同じ DB の同じ設定が、配線によって
    違う意味になる（conventions §1）。SQLite を Tauri と共有すると、ログインなしの端末の横で、LAN からの認証済みの
    書き込みが通る。
  - 不採用: ループバックだけに出す管理者相当の grant をテンプレートに入れる。プロキシの後ろではループバックの
    条件が守りにならない（ADR-0017 §6）。
  - 不採用: `BANTO_ALLOW_SETUP` を残す。ネットワーク越しに最初の管理者を作れる口が残る。
- **ログインなしの間の REST のアカウント**
  - **採用: ログインを断り、切り替えの時にトークンを失効させる（REST は読み取り専用）。** 「ログインなしの間は
    ネットワークから変えられない」が、listen の組み合わせの検査に頼らずに成り立つ。
  - 不採用: 認証済みのアカウントの書き込みは通す（今の形）。認証は通っているので穴ではないが、前提の文が偽になり、
    `banto-serve` の listen が保存した設定を見ないことと合わせて、柵がどこにあるかを説明できない。
- **キーが無いときの既定**
  - **採用: 新しい DB には migration が明示して入れ、欠落・破損は起動を止める。**
  - 不採用: コードの既定を on にする（計画書 §4.3 の文言）。v8 の DB でキーが消えただけで、admin 相当の
    ローカルセッションができる（fail-open）。
- **復元の候補の検査**
  - **採用: migration の履歴（版と checksum）を、予約のときと適用の直前に読み取り専用で確かめる。**
  - 不採用: 必須の表の名前だけを見る。v7 の checksum を持つ候補が通り、入れ替えの後に起動できなくなる（§9）。
  - **採用: 起動を止める検査も、同じ関数で入れ替えの前に通す。** 履歴が正常な v8 の候補でも、設定の欠落や
    管理者 0 で起動が止まりうる。
  - 不採用: 入れ替えの後の起動時の検査に任せる。正常だった元の DB が置き換わってから止まる。
- **初回の seed の条件**
  - **採用: 「seed 済みの印が無い」で判定し、C1 で 0014 と一緒に直す。**
  - 不採用: 「表が空」のまま、認証のキーの INSERT を後ろの PR へ回す。基準の migration を 2 回書き換える。
  - 不採用: seed の直しを C2b に回す。その間の main で、display の生成物が公開閲覧なしで起動する。
- **ログインとモードの切り替えの競合**
  - **採用: モードの世代を、発行の直前と認可の完了時に確かめる**（grant の世代のガードと同じ形）。
  - 不採用: 入口の判定と、切り替え直後の一括失効だけ。照合の await の間に切り替わると、旧い照合が発行する。
- **組み込みの行の保護の時期**
  - **採用: 行を入れる C1 で、照合と変更の対象から外す最低限の保護も入れる。**
  - 不採用: 保護を C2 に回す（計画書 §7 の分け方）。その間の main で行を消せ、消えた行は入れ直せない。
- **ログイン必須で管理者が 0 の DB**（N4）
  - **採用: 起動を止める。復旧は `banto-serve` の CLI か、§9 のオフラインの復元。**
  - 不採用: 黙ってログインなしへ戻す（fail-open）。
  - 不採用: Tauri の実行ファイルにも CLI を持たせる（§7）。

## 帰結

- **v8.0.0 は破壊的変更**。派生アプリは `0003_users.sql`・`0005_audit_log.sql` を差し替え、`0014_ui_settings.sql` を
  足し、**DB を作り直す**（移行の口は無い）。自分の migration を 0014 以降の番号で足している派生アプリは番号をずらす。
- `Identity` を自分で組み立てている派生アプリは `accountId` を載せる。載せないと持ち主のキーが `null` になり、
  持ち主つきの記憶が保存も復元もされない（黙って他人に渡すよりよい）。古い `account:` のキーの localStorage は残骸になる。
- 初回セットアップが無くなる（画面・REST の口・Tauri のコマンド・`AuthProvider.setup`・`BANTO_ALLOW_SETUP`）。
  新しい DB の既定がログインなしになる（0014 が設定を明示して入れる。キーが無い・読めない DB は起動が止まる。§5）。
  管理のユーザー一覧に `admin` が読み取り専用の 1 行として出る（件数・CSV・ユーザーを選ぶ口には出ない。§2）。
  `admin`（大小無視）と grant の固定 id のアカウントは作れない。Tauri のログインなしの監査の actor が `local` から
  `admin` に変わる。
- **ログインなしの間、REST でアカウントのログインができなくなる**（今はできる）。ログインなしへ切り替えると、
  アカウントのトークンは失効する。LAN から操作させるにはロックダウンが要る（§6）。
- **`banto-serve` は、ログインなしで閲覧公開も off の DB では listen しない**。ヘッドレスの最初の起動は、CLI
  （管理者の作成 + ロックダウン）が先（§7）。e2e と PostgreSQL の運用の手順が変わる。
- **組み込みの行が「ログインできる管理者」になる経路を作らない**。パスワードのリセット・CSV の取り込み・リストア・
  権限の個別付与（ADR-0031）・自動ログインの各経路を、実装 PR で 1 つずつ確かめて試験に入れる。
- **ログインなしの間は、ネットワークから業務・管理のデータを変えられない**。柵は §6 の 4 つ（`local` を REST に
  出さない・REST は読み取り専用・listen の条件を両方の配線が同じ関数で見る・ロックダウン）。§10 の試験で固定する。
- 監査の actor が `admin` の行は、Tauri のログインなし・印つきの grant・CLI から来る。経路は `actor_kind` で分かる
  （`actor_role` は実際のロール）。監査の表と wire に `actor_id`・`actor_kind`（`actorKind`）が増える。
- 監査を書く REST の handler は、bearer から引き直す形（`record_write` に headers を渡す形）をやめ、ガードが作った
  主体のスナップショットを受け取る。派生アプリが自分の handler で `record_write` / `actor_identity` を呼んでいる所は
  書き換えが要る。
- 復元は、migration の履歴が合わない候補を予約でも適用の直前でも断る。配線は migrator を `BackupService` に渡す。
  起動が止まった後のバックアップからの復旧は、予約のファイルを手で置くオフラインの手順（§9）。
- grant を足す派生アプリは、`audit_as_builtin_admin` を付けるかを grant ごとに決め、固定 id が既存のアカウントの
  名前と当たらないことを確かめる（当たれば起動が止まる）。
- [ADR-0017](0017-credential-less-grant.md) に追記する（§3 の acting id、監査と ui-settings の項、ロックダウンの条件）。
- 復元は、起動を止める条件（組み込みの行・必須の設定・ログイン必須での管理者）に当たる候補も、入れ替えの前に断る。
  起動を止める検査を足す派生アプリは、同じ検査を復元前にも掛ける（§9）。
- 初回の seed は「表が空」ではなく「seed 済みの印が無い」で動く。`first_boot.rs` をコピーしている派生アプリは
  差し替えが要る（差し替えないと、0014 の後は seed が 1 度も書かれない）。
- 実装は計画書 §7 の PR に分ける: C1（基準の作り直し・`account_uid` の採番・`kind` での数え直し・
  **組み込みの行の最低限の保護**・復元の検査・**初回の seed の条件の直し**）、C2（予約名・起動時の検査・帰属の印と
  認可時のスナップショット・`actor_id` / `actor_kind`）、C2b（初回セットアップの撤去・設定の明示と異常時の停止・
  ログインなしの間の REST と**モードの世代での直列化**・ロックダウンの条件・CLI）、C3（`accountId` を wire に載せる）、C4・C5（ui-settings）。計画書 §7 の表も
  この分け方にそろえた（2026-11-22）。食い違えばこの ADR が優先する。実装は C1 から始められる（2026-11-22 に `Accepted`）。
